### Bridge Protocol Overview

Source: https://github.com/openclaw/openclaw/blob/main/docs/gateway/bridge-protocol.md

An overview of the legacy Bridge protocol, its purpose, and its differences from the newer Gateway protocol.

```APIDOC
## Bridge Protocol (Legacy Node Transport)

### Description
The Bridge protocol is a **legacy** node transport mechanism that uses TCP with a JSON Lines (JSONL) format. It was designed to provide a secure boundary with a limited API surface compared to the full Gateway API. New node clients are recommended to use the unified Gateway WebSocket protocol instead.

**Note:** Current OpenClaw builds do not include the TCP bridge listener, and legacy `bridge.*` configuration keys are no longer supported. This documentation is for historical reference.

### Key Features
- **Security Boundary**: Exposes a small allowlist of functionalities instead of the entire gateway API.
- **Pairing and Node Identity**: Node admission is managed by the gateway and tied to a per-node token.
- **Discovery**: Nodes can discover gateways via Bonjour on LAN or connect directly over a tailnet.
- **Loopback WS**: The full WebSocket control plane remains local unless tunneled via SSH.

### Transport Details
- **Protocol**: TCP with JSON object per line (JSONL).
- **TLS**: Optional support when `bridge.tls.enabled` is true.
- **Default Port**: Legacy default listener port was `18790` (not active in current builds).
- **TLS Discovery**: When TLS is enabled, Bonjour/mDNS TXT records include `bridgeTls=1` and `bridgeTlsSha256`. These TXT records are unauthenticated and should not be used as an authoritative pin without out-of-band verification.
```

### Gateway Overview

Source: https://github.com/openclaw/openclaw/blob/main/docs/concepts/architecture.md

The Gateway acts as a central hub for all messaging surfaces, managing connections from control-plane clients and nodes over WebSockets.

```APIDOC
## Gateway Architecture Overview

### Description
The Openclaw Gateway is a single, long-lived process responsible for managing all messaging integrations (e.g., WhatsApp, Telegram, Slack). It exposes a WebSocket API for control-plane clients and nodes to connect and interact.

### Components
- **Gateway**: Manages provider connections, exposes a typed WebSocket API, validates incoming data, and emits various events.
- **Control-Plane Clients**: Applications like the macOS app, CLI, or web UI that connect to the Gateway via WebSocket for sending requests and subscribing to events.
- **Nodes**: Devices (macOS, iOS, Android, headless) that also connect via WebSocket, declaring `role: node` and providing device-specific capabilities and commands.

### Connection Details
- **Control-Plane Clients**: Connect to the Gateway's configured bind host (default `127.0.0.1:18789`) over WebSocket.
- **Nodes**: Connect to the same WebSocket server but identify with `role: node` and specify their capabilities.
- **Canvas Host**: Served by the Gateway's HTTP server under `/__openclaw__/canvas/` and `/__openclaw__/a2ui/` on the same port.

### Key Invariants
- Exactly one Gateway per host manages a single WhatsApp session.
- A mandatory handshake process must be completed upon connection.
- Events are not replayed; clients are responsible for refreshing on data gaps.
```

### Gateway WebSocket Protocol Frames

Source: https://github.com/openclaw/openclaw/blob/main/docs/concepts/typebox.md

Overview of the three types of frames used in the Gateway WebSocket protocol: Request, Response, and Event.

```APIDOC
## Gateway WebSocket Protocol Frames

### Description

The Gateway WebSocket protocol uses three distinct frame types for communication between clients and the server: Request, Response, and Event.

### Frame Types

- **Request Frame**: Used by the client to send a request to the server.
  - **Structure**: `{ type: "req", id, method, params }`
  - **Example**: `{ "type": "req", "id": "c1", "method": "connect", "params": { ... } }`

- **Response Frame**: Used by the server to respond to a client's request.
  - **Structure**: `{ type: "res", id, ok, payload | error }`
  - **Example**: `{ "type": "res", "id": "c1", "ok": true, "payload": { "type": "hello-ok", ... } }`

- **Event Frame**: Used by the server to push notifications or data to the client.
  - **Structure**: `{ type: "event", event, payload, seq?, stateVersion? }`
  - **Example**: `{ "type": "event", "event": "tick", "payload": { "ts": 1730000000 }, "seq": 12 }`

### Connection Flow

The initial communication must be a `connect` request from the client, followed by a `hello-ok` response from the server. Subsequent communication involves method calls and event subscriptions.
```

### Approval Workflow with Gateway and Operator UI (Conceptual)

Source: https://github.com/openclaw/openclaw/blob/main/docs/refactor/clawnet.md

Outlines a proposed centralized approval system where the gateway manages approval records and communicates with operator UIs. This flow ensures that approvals are handled consistently and securely, with clear semantics for resolution and timeouts.

```Pseudocode
// Gateway receives system.run intent from agent
function handleRunIntent(agentData) {
  const approvalRecord = createApprovalRecord(agentData.commandId);
  broadcastApprovalRequest(approvalRecord);
}

// Operator UI receives approval request and sends decision
function sendApprovalDecision(approvalId, decision) { // decision: 'approved' or 'denied'
  gateway.resolveApproval(approvalId, decision, userScope);
}

// Gateway processes approval resolution
function resolveApproval(approvalId, decision, scope) {
  if (!hasScope(scope, 'operator.approvals')) {
    reject('Unauthorized');
    return;
  }
  const record = getApprovalRecord(approvalId);
  if (record.status === 'settled' || isTimeout(record)) {
    reject('Approval already settled or timed out');
    return;
  }
  record.status = 'settled';
  record.decision = decision;
  logApproval(record);
  if (decision === 'approved') {
    invokeNodeCommand(record.command);
  }
}

```

Resumes a previously halted workflow after user approval.

```APIDOC
## POST /resume

### Description
Resumes a workflow that was halted for approval. Requires a valid resume token and an approval decision.

### Method
POST

### Endpoint
/resume

### Parameters
#### Request Body
- **action** (string) - Required - Must be 'resume'.
- **token** (string) - Required - The resume token obtained from a previous 'needs_approval' response.
- **approve** (boolean) - Required - True if the user approves the action, false otherwise.

### Request Example
```json
{
  "action": "resume",
  "token": "<resumeToken>",
  "approve": true
}
```

### Response
#### Success Response (200)
- **protocolVersion** (integer) - The version of the protocol.
- **ok** (boolean) - Indicates if the operation was successful.
- **status** (string) - The status of the operation (e.g., 'ok' or 'completed').
- **output** (array) - The structured result of the workflow execution after resuming.
- **requiresApproval** (object | null) - Contains approval details if the workflow requires further approval, otherwise null.

#### Response Example
```json
{
  "protocolVersion": 1,
  "ok": true,
  "status": "completed",
  "output": [...],
  "requiresApproval": null
}
```
```

### Complete Fixed Loop Example - OpenProse

Source: https://github.com/openclaw/openclaw/blob/main/extensions/open-prose/skills/prose/compiler.md

A comprehensive example showcasing the use of 'repeat' and 'parallel for' loops for generating ideas, research, and synthesizing information.

```prose
# Generate multiple variations of ideas
repeat 3:
  session "Generate a creative startup idea"

session "Select the best idea from the options above"

# Research the selected idea from multiple angles
let angles = ["market", "technology", "competition"]
parallel for angle in angles:
  session "Research this angle of the startup idea"
    context: angle

session "Synthesize all research into a business plan"
```

### Session Composition: Explicit Context Flow (Prose)

Source: https://github.com/openclaw/openclaw/blob/main/extensions/open-prose/skills/prose/guidance/patterns.md

Demonstrates the 'explicit context flow' pattern in Prose, emphasizing visible data flow through explicit context passing. The 'good' example shows how context is passed between sessions, while the 'bad' example highlights the risks of relying on implicit conversation history.

```prose
# Good: Explicit flow
let step1 = session "First step"
let step2 = session "Second step"
  context: step1
let step3 = session "Third step"
  context: [step1, step2]

# Bad: Implicit flow (relies on conversation state)
session "First step"
session "Second step using previous results"
session "Third step using all previous"
```
