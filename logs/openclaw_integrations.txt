### Interactive Buttons (Message Tool)

Source: https://github.com/openclaw/openclaw/blob/main/docs/channels/mattermost.md

Allows sending messages with clickable buttons that trigger agent responses upon user interaction.

```APIDOC
## Interactive buttons (message tool)

Send messages with clickable buttons. When a user clicks a button, the agent receives the selection and can respond.

Enable buttons by adding `inlineButtons` to the channel capabilities:

```json
{
  channels: {
    mattermost: {
      capabilities: ["inlineButtons"],
    },
  },
}
```

Use `message action=send` with a `buttons` parameter. Buttons are a 2D array (rows of buttons):

```
message action=send channel=mattermost target=channel:<channelId> buttons=[[{"text":"Yes","callback_data":"yes"},{"text":"No","callback_data":"no"}]]
```

### Button Fields

- `text` (required): display label.
- `callback_data` (required): value sent back on click (used as the action ID).
- `style` (optional): `"default"`, `"primary"`, or `"danger"`.

### User Interaction Flow

1. All buttons are replaced with a confirmation line (e.g., "? **Yes** selected by @user").
2. The agent receives the selection as an inbound message and responds.

### Notes

- Button callbacks use HMAC-SHA256 verification (automatic, no config needed).
- Mattermost strips callback data from its API responses (security feature), so all buttons are removed on click — partial removal is not possible.
- Action IDs containing hyphens or underscores are sanitized automatically (Mattermost routing limitation).

### Configuration

- `channels.mattermost.capabilities`: array of capability strings. Add `"inlineButtons"` to enable the buttons tool description in the agent system prompt.
- `channels.mattermost.interactions.callbackBaseUrl`: optional external base URL for button callbacks (for example `https://gateway.example.com`). Use this when Mattermost cannot reach the gateway at its bind host directly.
- In multi-account setups, you can also set the same field under `channels.mattermost.accounts.<id>.interactions.callbackBaseUrl`.
- If `interactions.callbackBaseUrl` is omitted, OpenClaw derives the callback URL from `gateway.customBindHost` + `gateway.port`, then falls back to `http://localhost:<port>`.
- Reachability rule: the button callback URL must be reachable from the Mattermost server. `localhost` only works when Mattermost and OpenClaw run on the same host/network namespace.
- If your callback target is private/tailnet/internal, add its host/domain to Mattermost `ServiceSettings.AllowedUntrustedInternalConnections`.
```

### Adapt Agent Tool to Tool Definition (TypeScript)

Source: https://github.com/openclaw/openclaw/blob/main/docs/pi.md

Adapts tools from pi-agent-core's `AnyAgentTool` type to pi-coding-agent's `ToolDefinition` type. This function maps the `execute` method signature, ensuring compatibility between the two agent core libraries. It handles optional properties like `label` and `description`.

```typescript
export function toToolDefinitions(tools: AnyAgentTool[]): ToolDefinition[] {
  return tools.map((tool) => ({
    name: tool.name,
    label: tool.label ?? name,
    description: tool.description ?? "",
    parameters: tool.parameters,
    execute: async (toolCallId, params, onUpdate, _ctx, signal) => {
      // pi-coding-agent signature differs from pi-agent-core
      return await tool.execute(toolCallId, params, signal, onUpdate);
    },
  }));
}
```

### HMAC Token Generation
To ensure secure interactions, an HMAC-SHA256 token must be generated and included in the `context._token` field. The process is as follows:

1.  **Derive Secret**: Generate a secret key using `HMAC-SHA256(key="openclaw-mattermost-interactions", data=botToken)`.
2.  **Build Context**: Create the context object containing all fields **except** `_token`.
3.  **Serialize Context**: Serialize the context object with **sorted keys** and **no spaces** (e.g., using `JSON.stringify` with compact output).
4.  **Sign Payload**: Sign the serialized context using `HMAC-SHA256(key=secret, data=serializedContext)`.
5.  **Add Token**: Append the resulting hex digest as `_token` to the context object.

**Python Example for HMAC Generation:**
```python
import hmac, hashlib, json

# Assume bot_token is available
bot_token = "your_bot_token_here"

secret = hmac.new(
    b"openclaw-mattermost-interactions",
    bot_token.encode(), hashlib.sha256
).hexdigest()

ctx = {"action_id": "mybutton01", "action": "approve"} # Add any other custom fields here

# Serialize context with sorted keys and no spaces
payload = json.dumps(ctx, sort_keys=True, separators=(',', ':'))

token = hmac.new(secret.encode(), payload.encode(), hashlib.sha256).hexdigest()

context = {**ctx, "_token": token}

print(f"Generated Context with Token: {context}")
```

**Common HMAC Pitfalls:**
- Ensure JSON serialization uses `sort_keys=True` and compact separators (`separators=(',', ':')`).
- Sign **all** context fields except `_token`.
- The secret must be deterministically derived from the bot token.
```

### Approval Workflow with Gateway and Operator UI (Conceptual)

Source: https://github.com/openclaw/openclaw/blob/main/docs/refactor/clawnet.md

Outlines a proposed centralized approval system where the gateway manages approval records and communicates with operator UIs. This flow ensures that approvals are handled consistently and securely, with clear semantics for resolution and timeouts.

```Pseudocode
// Gateway receives system.run intent from agent
function handleRunIntent(agentData) {
  const approvalRecord = createApprovalRecord(agentData.commandId);
  broadcastApprovalRequest(approvalRecord);
}

// Operator UI receives approval request and sends decision
function sendApprovalDecision(approvalId, decision) { // decision: 'approved' or 'denied'
  gateway.resolveApproval(approvalId, decision, userScope);
}

// Gateway processes approval resolution
function resolveApproval(approvalId, decision, scope) {
  if (!hasScope(scope, 'operator.approvals')) {
    reject('Unauthorized');
    return;
  }
  const record = getApprovalRecord(approvalId);
  if (record.status === 'settled' || isTimeout(record)) {
    reject('Approval already settled or timed out');
    return;
  }
  record.status = 'settled';
  record.decision = decision;
  logApproval(record);
  if (decision === 'approved') {
    invokeNodeCommand(record.command);
  }
}

```

### Telegram and WhatsApp Configuration

Source: https://github.com/openclaw/openclaw/blob/main/docs/help/faq.md

Configuration details for Telegram and WhatsApp integrations, including sender IDs and multi-agent routing.

```APIDOC
## Telegram and WhatsApp Configuration

### Telegram `allowFrom` Parameter
`channels.telegram.allowFrom` requires the **numeric Telegram user ID** of the human sender, not the bot username. The onboarding wizard can resolve `@username` to a numeric ID, but OpenClaw authorization strictly uses numeric IDs.

**Methods to obtain User ID:**
*   **Safer (no third-party bot):** DM your bot, then run `openclaw logs --follow` and read `from.id`.
*   **Official Bot API:** DM your bot, then call `https://api.telegram.org/bot<bot_token>/getUpdates` and read `message.from.id`.
*   **Third-party (less private):** DM bots like `@userinfobot` or `@getidsbot`.

See [/channels/telegram](/channels/telegram#access-control-dms--groups).

### Multi-Agent Routing for WhatsApp
Multiple users can share a single WhatsApp number with different OpenClaw instances using multi-agent routing. Bind each sender's WhatsApp DM (peer `kind: "direct"`, sender E.164 format) to a unique `agentId`. This provides each person with their own workspace and session store. Replies will originate from the same WhatsApp account, and DM access control (`channels.whatsapp.dmPolicy` / `channels.whatsapp.allowFrom`) remains global per WhatsApp account.

### Multi-Agent Routing for Different Agent Types
Yes, you can run different types of agents, such as a fast chat agent and an Opus coding agent. Use multi-agent routing to assign each agent its own default model. Then, bind inbound routes (based on provider account or specific peers) to the respective agents. Example configurations can be found in the [Multi-Agent Routing](/concepts/multi-agent) documentation.

### Resolve Authentication Profile Order

Source: https://github.com/openclaw/openclaw/blob/main/docs/pi.md

Determines the order of authentication profiles to use based on configuration, store, provider, and preferred profile. It helps in selecting the appropriate API key for requests.

```typescript
const profileOrder = resolveAuthProfileOrder({ cfg, store: authStore, provider, preferredProfile });
