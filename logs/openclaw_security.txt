### TLS Configuration and Fingerprint Pinning (TypeScript)

Source: https://github.com/openclaw/openclaw/blob/main/docs/refactor/clawnet.md

Illustrates how to reuse existing TLS runtime configurations and implement fingerprint pinning for secure communication. This involves setting up TLS on the server and verifying the server's certificate fingerprint on the client.

```TypeScript
import tls from 'tls';
import fs from 'fs';

// Server-side TLS setup (src/infra/bridge/server/tls.ts)
const options = {
  key: fs.readFileSync('server.key'),
  cert: fs.readFileSync('server.crt'),
  // ... other TLS options
};
const server = tls.createServer(options, (socket) => {
  console.log('Client connected');
  socket.end('Hello from server!');
});
server.listen(8000, () => {
  console.log('Server listening on port 8000');
});

// Client-side fingerprint verification (src/node-host/bridge-client.ts)
const serverCertificateFingerprint = 'expected-fingerprint-sha256'; // Replace with actual fingerprint

const clientOptions = {
  host: 'localhost',
  port: 8000,
  rejectUnauthorized: true, // Important for security
  checkServerIdentity: (hostname, cert) => {
    const fingerprint = tls.createSecureContext({ cert }).fingerprint;
    if (fingerprint !== serverCertificateFingerprint) {
      throw new Error('Server certificate fingerprint mismatch');
    }
    return undefined; // Certificate is valid
  },
};

const socket = tls.connect(clientOptions, () => {
  console.log('Connected to server');
  socket.write('Hello from client!');
});

socket.on('data', (data) => {
  console.log('Received:', data.toString());
  socket.end();
});

socket.on('error', (err) => {
  console.error('Socket error:', err.message);
});

```

### Device Keypair Generation and Authentication (TypeScript)

Source: https://github.com/openclaw/openclaw/blob/main/docs/refactor/clawnet.md

Demonstrates the process of generating a device keypair, deriving a device ID from the public key, and the subsequent authentication flow involving a nonce challenge and signature verification. This method avoids bearer token replay by issuing tokens based on proof-of-possession of the private key.

```TypeScript
import { generateKeyPair, sign, verify } from 'crypto';

// Device generates keypair once
const { publicKey, privateKey } = generateKeyPairSync('ec', { namedCurve: 'secp256k1' });

// deviceId = fingerprint(publicKey)
const deviceId = publicKey.export({ type: 'spki', format: 'pem' }); // Simplified representation

// Gateway sends nonce
const nonce = Buffer.from('some-random-nonce');

// Device signs nonce with its private key
const signature = sign('sha256', nonce, privateKey);

// Gateway verifies signature using the device's public key

### OpenCLaw Runtime and Token Authentication

Source: https://github.com/openclaw/openclaw/blob/main/docs/reference/wizard.md

Details on runtime selection and token authentication for the OpenCLaw daemon. Node.js is recommended, while Bun is not. The daemon validates tokens but does not persist plaintext values. Installation is blocked if tokens are unresolved or authentication modes are ambiguous.

```text
- **Runtime selection:** Node (recommended; required for WhatsApp/Telegram). Bun is **not recommended**.
- If token auth requires a token and `gateway.auth.token` is SecretRef-managed, daemon install validates it but does not persist resolved plaintext token values into supervisor service environment metadata.
- If token auth requires a token and the configured token SecretRef is unresolved, daemon install is blocked with actionable guidance.
- If both `gateway.auth.token` and `gateway.auth.password` are configured and `gateway.auth.mode` is unset, daemon install is blocked until mode is set explicitly.
```

```text

and include `x-forwarded-for`, `x-forwarded-proto`, and `x-forwarded-host` as
injected by Tailscale. HTTP API endpoints (for example `/v1/*`, `/tools/invoke`, and `/api/channels/*`)
still require token/password auth.

### Approval Workflow with Gateway and Operator UI (Conceptual)

Source: https://github.com/openclaw/openclaw/blob/main/docs/refactor/clawnet.md

Outlines a proposed centralized approval system where the gateway manages approval records and communicates with operator UIs. This flow ensures that approvals are handled consistently and securely, with clear semantics for resolution and timeouts.

```Pseudocode
// Gateway receives system.run intent from agent
function handleRunIntent(agentData) {
  const approvalRecord = createApprovalRecord(agentData.commandId);
  broadcastApprovalRequest(approvalRecord);
}

// Operator UI receives approval request and sends decision
function sendApprovalDecision(approvalId, decision) { // decision: 'approved' or 'denied'
  gateway.resolveApproval(approvalId, decision, userScope);
}

// Gateway processes approval resolution
function resolveApproval(approvalId, decision, scope) {
  if (!hasScope(scope, 'operator.approvals')) {
    reject('Unauthorized');
    return;
  }
  const record = getApprovalRecord(approvalId);
  if (record.status === 'settled' || isTimeout(record)) {
    reject('Approval already settled or timed out');
    return;
  }
  record.status = 'settled';
  record.decision = decision;
  logApproval(record);
  if (decision === 'approved') {
    invokeNodeCommand(record.command);
  }
}

```

- Description newline footgun: write Markdown via heredoc to `/tmp/ghsa.desc.md` (no `"\\n"` strings).
- Build patch JSON via jq: `jq -n --rawfile desc /tmp/ghsa.desc.md '{summary,severity,description:$desc,vulnerabilities:[...]}' > /tmp/ghsa.patch.json`
- GHSA API footgun: cannot set `severity` and `cvss_vector_string` in the same PATCH; do separate calls.
- Patch + publish: `gh api -X PATCH /repos/openclaw/openclaw/security-advisories/<GHSA> --input /tmp/ghsa.patch.json` (publish = include `"state":"published"`; no `/publish` endpoint).
- If publish fails (HTTP 422): missing `severity`/`description`/`vulnerabilities[]`, or private fork has open PRs.
- Verify: re-fetch; ensure `state=published`, `published_at` set; `jq -r .description | rg '\\n'` returns nothing.
```

### exec

Source: https://github.com/openclaw/openclaw/blob/main/docs/tools/index.md

Executes shell commands within the workspace. Supports various options for background execution, timeouts, and security.

```APIDOC
## exec

### Description
Run shell commands in the workspace. Supports background execution, timeouts, and elevated privileges.

### Method
POST

### Endpoint
`/tools/exec`

### Parameters
#### Path Parameters
None

#### Query Parameters
None

#### Request Body
- **command** (string) - Required - The shell command to execute.
- **yieldMs** (integer) - Optional - Timeout in milliseconds for auto-backgrounding. Defaults to 10000.
- **background** (boolean) - Optional - If true, runs the command immediately in the background.
- **timeout** (integer) - Optional - Timeout in seconds to kill the process. Defaults to 1800.
- **elevated** (boolean) - Optional - If true, runs the command with elevated privileges (requires specific configuration and agent capabilities).
- **host** (string) - Optional - The host to run the command on (`sandbox`, `gateway`, `node`). Defaults to `sandbox`.
- **security** (string) - Optional - Security level for the command (`deny`, `allowlist`, `full`).
- **ask** (string) - Optional - Controls user interaction for security prompts (`off`, `on-miss`, `always`).
- **node** (string) - Optional - The node ID or name to target when `host` is `node`.
- **pty** (boolean) - Optional - If true, requests a real TTY for the command.

### Request Example
```json
{
  "command": "ls -l",
  "background": true,
  "timeout": 60
}
```

### Response
#### Success Response (200)
- **status** (string) - The status of the command execution (e.g., "running", "completed").
- **sessionId** (string) - A unique identifier for the background session, if applicable.
- **output** (string) - The command output, if executed synchronously.
- **exitCode** (integer) - The exit code of the command, if completed.

#### Response Example
```json
{
  "status": "running",
  "sessionId": "abc123xyz789"
}
```
```

### Configure Host Browser Control in Sandboxed Sessions (JSON5)

Source: https://github.com/openclaw/openclaw/blob/main/docs/tools/chrome-extension.md

This configuration allows sandboxed sessions to control the host browser. It's necessary when the browser tool is restricted by default in a sandboxed environment and you need to interact with the host's Chrome instance. Ensure the tool policy does not deny browser access and specify `target="host"` when calling the browser tool if needed.

```json5
{
  agents: {
    defaults: {
      sandbox: {
        browser: {
          allowHostControl: true
        }
      }
    }
  }
}
```

### Integrate 1Password CLI for Secrets (JSON5)

Source: https://github.com/openclaw/openclaw/blob/main/docs/gateway/secrets.md

Configuration example for using the 1Password CLI as an 'exec' provider to retrieve secrets. It specifies the command path, allows symlinks, defines trusted directories, and passes necessary environment variables. The example shows how to map this provider to an OpenAI API key.

```json5
{
  secrets: {
    providers: {
      onepassword_openai: {
        source: "exec",
        command: "/opt/homebrew/bin/op",
        allowSymlinkCommand: true, // required for Homebrew symlinked binaries
        trustedDirs: ["/opt/homebrew"],
        args: ["read", "op://Personal/OpenClaw QA API Key/password"],
        passEnv: ["HOME"],
        jsonOnly: false,
      },
    },
  },
  models: {
    providers: {
      openai: {
        baseUrl: "https://api.openai.com/v1",
        models: [{ id: "gpt-5", name: "gpt-5" }],
        apiKey: { source: "exec", provider: "onepassword_openai", id: "value" },
      },
    },
  },
}
```
