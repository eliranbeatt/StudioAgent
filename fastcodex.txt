3) Gap Map: fast.txt vs Current Code
------------------------------------------------------------

1. Progressive Q backlog in `qaPairs`:
- Missing fields from fast contract: status/scope/blocking/order/version/follow-up metadata.
- Current `qaPairs` is too minimal for blocker-first deterministic progression and rebase-safe patching.

2. SDK deterministic question serving from persisted backlog:
- Exists for Flow (`flowQuestionSets`), not for SDK.
- SDK currently depends on emitted question blocks and message flow timing.

3. PlanDoc lifecycle and CAS:
- `memoryDocs` exists, but no canonical `planDoc.current + version + CAS retry` contract.

4. Async rebase loop:
- No `plan.rebase_from_answers_async` job that patches PlanDoc and question backlog on each submit.

5. Finalize package:
- SDK has planning/budget/quote tools and vNext compile, but no explicit "finalize.build_structured_package" contract aligned to fast.txt.

6. Deterministic compile/review/apply:
- vNext has deterministic compile (`convex/sdk/vnext/compiler.ts`), but SDK `changeset.compile/review` still run LLM in `convex/sdk/changeset.ts`.
- Needs stricter deterministic path for final apply safety.

7. Mode split (Planning Flow vs Chat Edit):
- Not implemented as explicit project/run mode contract yet.

------------------------------------------------------------
4) Recommended Architecture (Most Efficient for THIS Repo)
------------------------------------------------------------

Primary target: extend SDK vNext, do not build a fourth orchestration stack.

Reason:
- `sdkRuns` + stage artifacts + stage decisions + existing vNext validators already solve 60-70% of the workflow.
- Fastest path is hardening SDK vNext with qa backlog + rebase + deterministic finalization.
- Keep legacy and Flow tabs as fallback until rollout completion.

------------------------------------------------------------
5) Implementation Plan (Phased)
------------------------------------------------------------

Phase 1: Data contract hardening (no behavior change)
Files:
- `convex/schema.ts`
- `convex/agentData.ts`
- `convex/sdk/context.ts`
- `convex/sdk/schemas.ts`

Tasks:
1. Extend `qaPairs` with fast-flow fields:
   - `status`, `questionType`, `options`, `answer`, `answerText`, `scopeType`, `scopeKey`, `sectionPath`, `blockingLevel`, `orderKey`, `createdFrom`, `followUp`, `triggeredBy`, `dedupeKey`, `version`.
2. Keep legacy fields (`question_he`, `answer_he`) for compatibility.
3. Update normalizers/selectors in `agentData` and `sdk/context` to expose both legacy and new fields.
4. Add indexes needed for deterministic serving:
   - by project+status
   - by project+blockingLevel
   - by project+orderKey
   - by project+scopeKey

Definition of done:
- Existing tabs still work unchanged.
- New fields can be written/read without breaking old records.

Phase 2: SDK Question Backlog service (deterministic persisted serving)
Files:
- New `convex/sdk/questions.ts`
- `convex/sdk/api.ts`
- `convex/sdk/vnext/pipeline.ts`
- `src/app/projects/[id]/sdk-agent/page.tsx`

Tasks:
1. Add SDK question APIs:
   - `sdk.questions.nextSet(runId|projectId)`
   - `sdk.questions.submitAnswers(runId, questionIds/answers, intent)`
2. Serve blocker-first deterministic sets directly from persisted `qaPairs` (not from transient model output).
3. Enforce ordering policy:
   - global blockers first
   - then element blockers grouped by element order
   - each set may include blocker + helpful/optional questions/suggestions for that active scope
4. Add SDK cursor state (run-level or project-level) using:
   - `lastServedOrderKey`
   - `lastServedAt`
5. Update SDK UI to load/submit current set via these APIs.
6. Keep compatibility fallback to block-based questions while migrating.

Definition of done:
- SDK Question lane always recovers from refresh and never depends on in-flight tool calls.

Phase 3: Draft + seed (single heavy call aligned to fast.txt)
Files:
- `convex/sdk/prompts.ts`
- `convex/sdk/registry.ts`
- New `convex/sdk/planner.ts` (or `convex/sdk/vnext/planner.ts`)
- `convex/sdk/vnext/stages.ts`
- `convex/sdk/vnext/skillBridge.ts`

Tasks:
1. Add tool: `draft.plan_and_questions` (gpt-5.2, fast/no reasoning).
2. Output:
   - `PlanDoc v1` markdown
   - seed question backlog with blocker/helpful/optional metadata
3. Persist `PlanDoc v1` to canonical memory doc kind `PROJECT_CONTEXT` (typed payload/versioned body).
4. Insert seed questions to `qaPairs` with deterministic `orderKey`.
5. Initial planning is single-pass and auto-approved in agent mode (no validation gate in this stage).

Definition of done:
- New project can go from context to persisted plan+question backlog in one run.

Phase 4: Async rebase after each answer submit
Files:
- New `convex/sdk/rebase.ts`
- `convex/sdk/questions.ts`
- `convex/sdk/vnext/pipeline.ts`
- `convex/sdk/telemetry.ts`

Tasks:
1. On answer submit, enqueue async rebase job:
   - input: current PlanDoc/version + newly answered rows + open backlog snapshot
2. Rebase output contract:
   - `planDocPatch` (or full markdown)
   - `questionsPatch` (`add`, `resolve`, `promote`, `dedupe`)
3. Enforce patch rules in code:
   - never reopen answered
   - add follow-ups instead
   - churn cap (max new questions per submit)
   - blocker promotion only when truly blocking
4. CAS/version safety:
   - apply only if PlanDoc version matches; otherwise reload+retry once.

Definition of done:
- User sees next question instantly.
- Plan/backlog rebases asynchronously without race corruption.

Phase 5: Finalize package + deterministic compile/apply
Files:
- New `convex/sdk/finalize.ts`
- `convex/sdk/vnext/compiler.ts`
- `convex/sdk/changeset.ts`
- `convex/sdk/vnext/validators/*`
- `convex/sdk/dispatch.ts`

Tasks:
1. Add `finalize.build_structured_package` tool:
   - consumes PlanDoc + answered/assumed qaPairs + context.
2. Finalize is always available (including with open questions), using assumptions on unanswered items.
3. Pricing order in finalize:
   - internal price memory -> web/logged research -> estimate with confidence+assumptions.
4. Move compile path to deterministic code-first for finalize (reuse and harden `compileDeterministicChangeSet`).
5. Keep LLM review optional/advisory; hard validation remains code gates.
6. Apply policy:
   - planning-flow mode auto-applies (no approval step in this mode).

Definition of done:
- Finalize emits complete elements/tasks/accounting/quote package and safe changeset apply path.

Phase 6: Post-Quote Chat Edit mode
Files:
- `convex/sdk/vnext/contracts.ts`
- `convex/sdk/vnext/pipeline.ts`
- New `convex/sdk/changeRequests.ts`
- `src/app/projects/[id]/sdk-agent/page.tsx`

Tasks:
1. Add explicit mode:
   - `PLANNING_FLOW`
   - `CHAT_EDIT`
2. Parse chat change requests -> required clarifications -> deterministic changeset compile/apply.
3. Guardrails for high-impact deletes/cost deltas (manual confirm).

Definition of done:
- After first quote, user can request edits conversationally with controlled changesets.

8) Locked Decisions (Confirmed)
------------------------------------------------------------

1. Question source of truth:
- SDK serves questions directly from `qaPairs`.

2. Ordering policy:
- global blockers first
- then element blockers by element order
- each set includes blockers plus helpful/optional questions/suggestions for the same active scope.

3. Finalize availability:
- always available; can proceed with assumptions.

4. Initial planning and apply behavior:
- initial planning is single-pass with no validation gate
- planning-flow mode is auto-approved/auto-apply.

5. Canonical PlanDoc kind:
- use `memoryDocs.kind = PROJECT_CONTEXT`.

------------------------------------------------------------
9) Immediate Build Order (Best Efficiency)
------------------------------------------------------------

1. Phase 1 (schema + compatibility)  
2. Phase 3 (draft+seed heavy call)  
3. Phase 2 (SDK deterministic question service)  
4. Phase 4 (async rebase loop)  
5. Phase 5 (finalize + deterministic compile/apply)  
6. Phase 6 (chat edit mode)  

Reason for this order:
- It establishes canonical plan/backlog first, then deterministic serving/rebase/finalize on top.
