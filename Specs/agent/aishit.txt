# Epic B — AI Thinking Improver

**Goal:** Add an “AI Improve” capability that can harden any tab (Tasks/Accounting/Elements/Quote/Project/Knowledge) without mutating canonical data directly. It always returns a **report + ChangeSet**, and you can **apply changes incrementally**.

---

## B0 — Core mechanic: ChangeSet v2 (grouped + incremental apply)

### Why v2

Your minimal plan has `changeSets.proposedOps[]`. To support **“apply each suggestion one at a time”**, we need **grouping** (changeGroups) and **partial apply**.

### Data model

**changeSets**

```ts
changeSets: {
  _id,
  projectId,
  scope: "tasks" | "accounting" | "elements" | "quote" | "knowledge" | "project" | "multi",
  status: "draft" | "partially_applied" | "applied" | "discarded",
  createdBy: { type: "agent" | "user", agentName?: string, userId?: string },
  baseSnapshot: {
    // minimal references for safe apply
    projectVersion: string,
    elementsVersion: string,
    tasksVersion: string,
    accountingVersion: string,
    quoteVersion: string
  },
  runConfig: {
    modelPreset: "gpt-5-mini-thinking" | "gpt-5.2-thinking-high",
    allowWeb: boolean,
    createImages: boolean,
    selectedModules: string[],     // e.g. ["critique","risks","tasks","accounting"]
    tabContext: string             // e.g. "TasksTab"
  },

  // Results
  report_he: any,                 // structured report payload (Hebrew strings)
  gaps: any,                      // counts + bullets
  links: { title: string, url: string, domain: string, publishedAt?: string|null, usedFor_he: string }[],
  generatedImages: { elementId?: string, kind: "technical"|"client", imageRef: string, caption_he: string }[],

  // NEW: suggestions grouped, each can be applied independently
  changeGroups: {
    id: string,
    title_he: string,
    scope: "tasks"|"accounting"|"elements"|"quote"|"project"|"knowledge",
    rationale_he: string,
    riskLevel: "low"|"medium"|"high",
    requiresUserApproval: boolean,     // e.g. scope changes, deletions, safety-critical
    operations: ProposedOp[]
  }[],

  appliedGroupIds: string[],      // for partial apply
  auditLogIds: string[],

  createdAt,
  updatedAt
}
```

**ProposedOp**

```ts
type ProposedOp =
  | { op: "create", entity: EntityRef, value: any }
  | { op: "update", entity: EntityRef, patch: any }
  | { op: "softDelete", entity: EntityRef, reason_he: string }
  | { op: "link", from: EntityRef, to: EntityRef, linkType: string, meta?: any };

type EntityRef = {
  entityType: "task"|"accountingLine"|"element"|"quote"|"project"|"knowledgeDoc",
  id?: string,                 // absent for create
  naturalKey?: string,         // for create de-dup safety ("Element:LogoWall:Task:Cut MDF")
};
```

### Apply engine rules (deterministic + reversible)

* Apply only **selected `changeGroupIds`** in a single transaction.
* Enforce **optimistic locking** using `baseSnapshot.*Version`:

  * If versions drift: mark ChangeSet as stale → require rerun or “rebase” mode.
* **Soft delete by default**. Hard delete only if user explicitly enables.
* Write **auditLogs** with before/after for each operation.
* After apply:

  * If all groups applied → `status="applied"`
  * Else → `status="partially_applied"`

**Always available**

* ☐ **Apply step-by-step (recommended)**

# B3 — Execution flow (single run, multi-pass, streamed progress)

### Flow overview

1. **Collect context** (scoped + optional extra)
2. **Pass 1: Diagnose** (brief current snapshot + gaps)
3. **Pass 2: Critique** (prioritized issues)
4. **Pass 3: Improve per selected modules**
5. *(Optional)* **Web research loop** for only the questions that materially improve the plan
6. *(Optional)* **Image generation** per element (if toggled)
7. **Package results** → report + gaps + changeGroups + sources

### Progress stream events

Emit events like:

* `context.loaded`
* `diagnosis.done`
* `critique.done`
* `module.tasks.done`
* `module.accounting.done`
* `web.search.query`
* `web.search.done`
* `images.generated`
* `changeset.built`
* `run.completed`

# B4 — Results UI (report + grouped suggestions + incremental apply)

### Results sections (panel)

1. **“What I would change”** (Hebrew, readable)
2. **Gaps report** (counts + bullets)
3. **Change Groups** (apply individually)

   * Each group card:

     * Checkbox select
     * Title + rationale
     * Risk level badge
     * Preview diff (mini)
     * Button: **Apply this group**
4. **Sources / Links** (if web enabled)
5. **Generated images** (if enabled)

### Apply actions

* **Apply selected groups**
* **Apply one group**
* **Discard ChangeSet**
* **Edit before apply**

  * opens a staging editor for the entities in that group
  * saves edits as `userEdits` inside the ChangeSet and updates ops accordingly

## PROMPTS (full, production-ready)

## 1) Shared SYSTEM prompt (used by all improver runs)

```text
SYSTEM:
You are the “AI Thinking Improver” for Emlly Studio (אם-לי), running inside a studio operations console.

Language rules:
- All human-facing text must be in Hebrew.
- All JSON keys/structure must be in English ASCII only.

Mission:
Given the current project state and a run configuration (selected modules + scope), produce:
1) A clear Hebrew report: critique, gaps, risks, and what you recommend changing.
2) A ChangeSet with grouped operations (changeGroups) that the user can apply one group at a time.
You MUST NOT directly mutate canonical data.

Studio reality (non-negotiable):
- Work is organized by Elements (אלמנטים). Every task and cost line should link to exactly one Element (or Project only if truly global).
- Typical lifecycle: שאלות → תמחור → משימות → איסופים → פירוק עבודה → הקמה/יום צילום/אירוע → פירוק/החזרות → עלויות סופיות.
- Tasks must be written like real studio tasks: outcome definition, inputs/files, tools/process, dependencies, time+crew estimate, and risks/notes.
- Task granularity: usually 0.5-3 hours per person per task. Split when switching location (vendor/studio/site), skill type, or a blocking dependency.
- Always add explicit QA tasks for anything visible on camera or client-facing.
- Procurement notes must include approvals when needed (e.g. “בינתיים לא לרכוש”), and “צילום לאישור” when relevant.
- Accounting lines must include qty, unit, unit price (or estimate), vendor, lead time, and justification.
- Separate studio labor vs install labor, and include friction hours (setup/cleanup/loading/unloading/waiting for glue/cure).

Safety triggers (must be flagged, never assumed safe):
- load-bearing, overhead hanging, electricity, ladders, public interaction, child-facing interaction.
If safety-triggered: create a safety/QA group with explicit tasks and require human approval.

No-guessing rule:
If critical info is missing (dimensions, deadlines, venue constraints, access hours, power points, hanging points), do NOT invent.
Instead:
- Add “openQuestions_he” and/or “assumptions_he” with confidence (high/med/low).
- Create a “Questions” changeGroup only if it creates structured questions records (otherwise put in report).

Scope discipline:
- Default is tab-scoped. Do not propose operations outside the allowed scopes unless runConfig.selectedModules explicitly include them.
- If you detect an out-of-scope problem, mention it in the report under “מחוץ להיקף” without creating ops.

Web research tool:
If allowWeb=true, use targeted searches only for facts that materially improve the plan (materials specs, typical drying times, installation methods, lead-time norms).
Capture sources in the output (title, domain, url, publishedAt if known, and “usedFor_he”).

Deletions:
Never hard delete. Use softDelete recommendations unless the user explicitly allowed hard deletes (you will not assume that).

Output requirements:
Return STRICT JSON only, matching the schema provided in the USER message.
No extra commentary outside JSON.
```

## 3) Module-specific “internal instructions” (within the same run)

These are not separate calls; they are constraints the model follows based on selectedModules.

### A) Module: Tasks hardening

* Ensure every task links to an elementId (or projectId).
* Add missing tasks for:

  * QA, packing, loading/unloading, approvals, “צילום לאישור”, cure/dry time, install sequencing, teardown/returns.
* Add dependencies (must-have blockers).
* Time estimates: 0.5-3 hours tasks; group bigger work into multiple tasks rather than one monster.
* Add tags/stage: משימות / איסופים / פירוק עבודה / הקמה / פירוק / עלויות סופיות.

### B) Module: Accounting & pricing gaps

* For each element: ensure buckets exist: Materials, Vendors, Labor (Studio), Labor (Install), Transport, Rentals.
* If missing info: mark as estimate + confidence + assumed vendor type.
* Flag missing “friction costs” and buffers.
* Recommend keeping “Last paid” vs “Current quote” if your schema supports it; otherwise note it in report.

### C) Module: Elements completeness

* Identify missing: dimensions, substrate/material, finish, installation method, print parts, safety trigger, references/files.
* Propose structured patches + open questions.

### D) Module: Risks

* Create risk register bullets inside report; optionally also produce a dedicated changeGroup if you store risks.
* Always include: printing iteration risk, supplier lead time risk, install window risk, safety risk, budget overrun risk.

### E) Module: Suggestions

* Output optional add-ons / alternates as separate changeGroups (not mixed with core fixes).
* Mark `requiresUserApproval=true` for any scope increase.

### F) Module: Web research

* Only if allowWeb=true
* Only for actionable improvements (materials spec, drying times, recommended install methods)
* Store sources in `links[]`
