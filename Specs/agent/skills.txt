According to your uploaded (undated) **Emlly Studio – Agent Prompts v7** and your **StudioOps Workflow / Pricing playbooks**, here’s a full end-to-end dev plan that fits your current app: **one Agent UI (chat + structured blocks), zero auto-running skills, immediate skill recommendations from project state, Clarifications before any major “builder” skill, and ChangeSets for approval**.
Key contracts we’ll preserve: **Hebrew values for user-facing text + English ASCII keys for machine JSON**, plus a strict “blocks + ChangeSet” output format. 

---

## 0) Product principles (non-negotiables)

### 0.1 No automatic skills

* No background runs.
* No “guardrails that silently run.”
* The only “always” behavior is **UI showing recommended skills** (rule-based, deterministic).

### 0.2 Two-step gating for major builders

For **Elements / Tasks / Accounting(BOM) / Quote**:

1. **Clarifications** asks 3–8 blocking questions
2. After you answer → **Builder** returns a **ChangeSet** for approval

### 0.3 Contract-safe outputs

From v7:

* **JSON keys must be English ASCII**; user-facing values are Hebrew. 
* Output prefers `blocks[]` and if you emit a ChangeSetBlock or QuestionsBlock you also emit next-step suggestions. 
* Tasks must be realistic work packages (1–4h small, 1–2d large) with atomic checklists. 
* Accounting lines must link to tasks (taskId or temp). 

### 0.4 Suggestions are *selectable*, never forced

Your workflow playbook already defines the Suggestions schema with payloads and Hebrew text.

## 1) High-level architecture

### 1.1 Components

**Frontend (Next.js)**

* Existing Agent tab UI (chat + structured panes)
* “Recommended skills” panel shown immediately (no LLM)

**Backend (Convex)**

* `skillRunner` action: executes one chosen skill, validates JSON, stores run + blocks
* `skillRecommender` query: deterministic scoring from project state → list of recommended skills
* `changeSet.apply` mutation: applies ops to canonical tables
* `changeSet.discard` mutation: discards
* `qaStore` mutation: stores raw user Q/A pairs for gating + memory

**LLM gateway**

* Single function `callSkillLLM(skillId, context, params)` with:

  * model preset
  * optional web-search tool (only for allowed skills)
  * strict JSON validation + retry with “repair” prompt if needed

### 1.2 Where this fits your current app

Your repo already includes:

* `/admin/skills` for skill editing/storage 
* agent run telemetry tables (`agentRuns`, `conversations`) 
* ingestion + knowledge pipeline (RAG) you can reuse for “context docs” and citations if needed

## 5) Skill recommendation engine (instant, no LLM)

### 5.1 ProjectStateDigest (computed query)

Build a digest similar to:

* `elementsCount`, `elementsDraftCount`, `elementsApprovedCount`
* `tasksCount`, `tasksBlockedCount`, `tasksHaveDepsPct`
* `accountingHasLines`, `accountingLinkedToTasksPct`
* `quoteStatus` (none/draft/approved)
* `eventDateDaysAway`
* `printsPendingQaCount`
* `receiptsUnmappedCount`

### 5.2 Scoring rules (deterministic)

Return top 5 “Recommended skills now” + grouped secondary.

Examples:

* No elements → recommend `CLARIFICATIONS_GATE(target=ELEMENTS_BUILDER_FULL)` + `CONSULTANT_CHAT`
* Has elements but no tasks → gate→tasks
* Has tasks but no accounting → gate→accounting
* Has accounting but no quote → gate→quote
* Prints uploaded → `PRINT_QA`
* Receipts uploaded/unmapped → `RECEIPT_PARSE_AND_MAP`

This matches your desire: user sees suggested skills immediately and can start chatting.

## 8) Execution pipeline (backend “Skill Runner”)

### 8.1 `runSkill(projectId, skillId, params)`

Steps:

1. Load skill definition from `skills`
2. Compute context bundle:

   * project + elements + tasks + accounting + quote snapshot
   * selected IDs from params
   * clarification answers (if any)
   * relevant doc summaries (optional)
3. Enforce preconditions:

   * If skill requires clarifications and not satisfied → run `CLARIFICATIONS_GATE` instead
4. Call LLM with:

   * shared header (v7) + skill addon
   * tool permissions (web search only if allowed + toggled)
5. Validate strict JSON:

   * ensure no Hebrew keys (hard rule) 
   * validate `lineType` is only material/work 
6. Store `skillRun` + normalized blocks
7. Return blocks to UI

### 8.2 ChangeSet apply

* Resolve temp IDs (taskTempOrId) per v7 linking strategy 
* Apply ops transactionally
* If conflict: show “cannot apply” with targeted fix suggestions (don’t silently partially apply)
