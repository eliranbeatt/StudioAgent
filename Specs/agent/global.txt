
# Epic E — Global Navigation (Studio level)

## Goal

Add a **persistent studio-level top navigation** that is visible **everywhere** (including inside projects) and provides these **primary tabs**:

* **Projects** → `/projects` (already exists)
* **Customers** → `/customers` (new studio-level page, separate from `/management/customers`)
* **Tasks** → `/tasks` (new global tasks page)
* **Accounting** → `/accounting` (new global accounting dashboard)

This must **coexist cleanly** with what you already have:

* Global shell + sidebar (Projects / RAG Chat / Ingestion / Management / Admin)
* Management Hub (`/management/*`) with its own internal sidebar and all ops tooling
* Project workspace (`/projects/[id]/*`) with project sidebar tabs (Overview / Agent / Studio / Elements / Accounting / Tasks / Quote / Knowledge / Receipts / Graveyard / Suggested…)

---

# 1) Information Architecture update

## 1.1 Primary nav (new): “Studio Tabs”

A new top bar in the **global shell**:

**Projects | Customers | Tasks | Accounting**

### Active rules

* Any route starting with `/projects` → **Projects** tab is active
* `/customers` and `/customers/[id]` → **Customers**
* `/tasks` → **Tasks**
* `/accounting` → **Accounting**
* Everything else (RAG/ingestion/management/admin) doesn’t activate Studio Tabs, but the bar remains visible.

## 1.2 Three more nav categories (explicit, aligns to your current app)

You already have “tools/admin/ops” areas. We’ll formalize them into **3 categories** (for sidebar grouping + mental model consistency):

1. **Tools**

   * RAG Chat (`/rag-chat`)
   * Ingestion (`/ingestion`, `/ingestion/connectors`)

2. **Ops Hub**

   * Management (`/management`) *(keeps its own internal sidebar: customers/vendors/catalog/prices/purchases/receipts/employees/settings/tracing/proposed…)*

3. **System / Admin**

   * Admin root (`/admin`)
   * Skills (`/admin/skills`)
   * Enrichment (`/admin/enrichment`)

So the experience becomes:

* **Top bar = Studio execution views**
* **Sidebar = Tooling/Ops/System entry points** (grouped, not removed)

# 3) Data + Convex plan (update based on what you already have)

## 3.1 Customers: **already exists**

Your app already has:

* Customer autocomplete in **NewProjectDialog** using `api.customers.listActive`
* Management customers UI using `api.customers.listWithContacts`, `findOrCreateByName`, `addContact`

So Epic E **does NOT add** a new customers table.

### What we add for studio-level customers pages

Create a new “studio customers view API” layer (thin wrappers around existing tables/queries), so `/customers` doesn’t need to reuse the management UI wholesale:

**Convex additions (recommended file: `convex/customersStudio.ts`)**

* `listCustomersStudio({ status?: "active"|"archived", query?: string })`

  * returns minimal rows: `id, name, status, contactsCount?, updatedAt`
* `getCustomerStudio({ customerId })`

  * customer core info + contacts summary
* `listProjectsByCustomer({ customerId, includeArchived?: boolean })`

  * returns: `projectId, projectName, projectStatus, updatedAt, eventDate?`
* `getCustomerRollups({ customerId })` (phase 2)

  * totals: quoted vs planned vs actual (if receipts exist)

> Implementation detail: you can reuse existing customer ids (Convex `Id<"customers">`) or a slug field if you already have one. Don’t invent a second “customerId business id” unless you already store it.

## 3.2 Projects linkage (don’t re-design; just use what’s there)

NewProjectDialog already selects/creates customers, and `api.projects.createProjectFromModal` stores the chosen customer. Epic E only requires that `/customers/[id]` can query projects by customer.

If your `projects` table already has `customerId`, add (or confirm) an index:

* `projects.by_customerId`

If you only store `customerName`, add `customerId` now (migration-safe, additive) and keep snapshot `customerName` for display stability.

## 3.3 Global Tasks: add a global query + indexes

You already have robust project tasks UI and a `tasks` table; but project pages likely query by `projectId`.

Add:

**Convex query: `tasks.listGlobal({ filters, pagination })`**
Filters:

* `projectId?`
* `assigneeId?` (employees)
* `workType?` (your StudioWorkType / category mapping)
* `status?`
* `dueFrom?, dueTo?`
* `text?` (search title/description)

Returns:

* task fields + `projectName`, `customerName/customerId` (join via projects table)

**Indexes (only if missing)**

* `tasks.by_projectId` (likely exists)
* `tasks.by_status`
* `tasks.by_assigneeId`
* `tasks.by_dueDate`
* `tasks.by_workType` (or by category enum)

## 3.4 Global Accounting: aggregate view query

You already have a project accounting workspace (`/projects/[id]/accounting`) with Summary/Materials/Labor, and you also have receipts flows (management-wide + project-specific).

Add:

**Convex query: `accounting.getGlobalSummary({ projectStatus?: "active"|"archived", customerId?: Id, currency?: string })`**
Returns:

* Global totals:

  * `plannedMaterialsTotal`
  * `plannedLaborTotal`
  * `plannedCostTotal`
  * `sellTotal` (using project margin fields)
* Per-project rows:

  * `projectId, projectName, customerName`
  * `materialsTotal, laborTotal`
  * `riskPct, overheadPct, profitPct`
  * `sellTotal`
  * `approvedBudget` (from approved quote/baseline if you store it)
  * `gap` fields (if you already compute them in project summary)

**How to compute**

* MVP: compute planned totals by summing `materialLines` + `workLines` grouped by `projectId` (your dataset scale is studio-scale; this is fine)
* If you want actuals: sum approved receipt line allocations (only if already modeled cleanly)

  * Customers (users icon)
  * Tasks (checklist icon)
