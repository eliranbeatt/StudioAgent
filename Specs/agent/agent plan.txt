# 1) Product spec: what the Agent Tab must do

## 1.1 Goals

* Replace the bloated “skills” system with **one assistant** that:

  * listens,
  * asks only the minimum blockers,
  * suggests realistic options (elements / build approaches),
  * proposes **ChangeSets** you can Apply/Discard,
  * and keeps everything mapped to your real workflow: **Elements → Tasks → Accounting → Quote → Production**.

## 1.2 Non-goals (v1)

* No autonomous “full plan every turn”
* No background automation
* No complex multi-agent routing
* No forced mode switching (mode is a user nudge)

# 2) UX: Single tab layout + “flowing blocks”

## 2.1 Layout (single window)

**Header**

* Stage selector (3): **IDEATION / QUOTE / BREAKDOWN**
* Mode selector (3): **CHAT / QUESTIONS / SUGGESTIONS**
* Optional: “Prompt version” badge (for debugging)

**Body (3 columns)**

1. **Left panel: Conversations**

   * Conversation list (per project)
   * New conversation button
2. **Center: Chat thread**

   * Message stream (virtualized)
   * Assistant messages can include **one interactive block**
   * Composer at bottom (text input + send)
3. **Right panel: Elements inspector**

   * Approved elements list
   * Draft elements list
   * Selected element details (already implemented in your app, per your note)

## 2.2 What “Mode” means (without breaking flow)

Mode is a **hint** to the agent:

* **CHAT**: normal conversation
* **QUESTIONS**: prefer asking clarifications (render a Clarification block sooner)
* **SUGGESTIONS**: prefer suggesting options/cards sooner

**Important:** regardless of mode, the agent may render:

* Clarification block (structured form)
* Suggestion block (selectable cards)
* ChangeSet block (Apply/Discard)

## 2.3 Interactive blocks (in-chat)

Exactly these 3 block types (v1):

1. **ClarificationBlock**: fields + quick options + submit
2. **SuggestionBlock**: selectable cards (single or multi) + submit
3. **ChangeSetBlock**: diff preview + Apply/Discard

After you submit a block → the chat continues normally.

# 5) Agent runtime: context builder (critical to avoid bloat)

## 5.1 Inputs sent to the LLM per turn

Send only what helps; avoid “entire database”.

**Always include**

* `project`: name, stage, pricing defaults
* `conversation`: last ~20 messages (text + event summaries)
* `selectedElementIds` (from UI)
* `elements`: summaries of:

  * selected elements (full-ish)
  * plus top 5 recently updated elements (thin summary)
* `rollups` (thin):

  * per selected element: estimate total, actual total, open tasks count, printing count

**Include on demand**

* If stage = BREAKDOWN and user asks for detailed tasking: include tasks for selected elements
* If user asks about accounting: include accounting lines for selected elements
* If user asks about print: include print parts for selected elements

## 5.2 “Working memory” compression

Store a short server-side summary per conversation (optional but recommended):

* `knownFacts_he[]`
* `openQuestions_he[]`
* `assumptions_he[]`

Update it whenever:

* clarification form submitted
* suggestions selected
* changeset applied

This keeps prompts small and avoids regressions.

# 6) LLM response contract (strict)

Use the prompt pack file you downloaded. It enforces:

* **one next-best action**
* **max one block**
* Hebrew user text, English keys
* stage + mode aware behavior
* ChangeSet-only writes

**Implementation detail (recommended):**

* LLM returns:

  * `assistantText_he`
  * optional `block`
  * if block is ChangeSetBlock: include `proposedChangeSet` in `block` payload (or in `block.items[].payload`)
* Server validates with Zod.
* Server persists ChangeSet and replaces the embedded payload with `changeSetId` before writing the assistant message.

That way the DB remains the source of truth for ChangeSets.

# 7) The “flowing assistant” state machine (UI)

Single reducer (or XState) in the Agent Tab:

**States**

* `IDLE`
* `SENDING_MESSAGE`
* `WAITING_FOR_AGENT`
* `WAITING_FOR_BLOCK_SUBMIT` (Clarification/Suggestion)
* `WAITING_FOR_CHANGESET_DECISION` (Apply/Discard)
* `ERROR`

**Transitions**

* user sends text → `SENDING_MESSAGE` → `WAITING_FOR_AGENT`
* agent responds with block:

  * clarification/suggestions → `WAITING_FOR_BLOCK_SUBMIT`
  * changeset → `WAITING_FOR_CHANGESET_DECISION`
* submit block → add event message → call `agentRespond` → back to `WAITING_FOR_AGENT`
* apply/discard → mutation → add event message → call `agentRespond` or return to `IDLE` (your choice)

Recommended: after Apply/Discard, do one short agent follow-up (“אוקיי, מה הצעד הבא?”) automatically.

# 9) Error handling & guardrails (must-have)

## 9.1 LLM output invalid JSON

* Server tries one “repair” pass (optional)
* If still invalid:

  * store assistant message as plain text: “הייתה שגיאה בפורמט, נסה שוב”
  * log the raw output for debugging

## 9.2 Apply conflicts (element rev mismatch)

* `applyChangeSet` returns:

  * `CONFLICT`
  * list of element IDs + current rev
* UI shows a conflict card:

  * “האלמנט השתנה מאז ההצעה. לרענן הצעה?”
* On refresh: emit an event and call agent again (it should re-propose a new changeset)

## 9.3 Safety-critical flags

If agent sets `safetyCritical=true`, enforce one of:

* auto-add QA task: “בדיקת בטיחות/מהנדס”
* or block apply with a warning requiring confirmation (your choice)
