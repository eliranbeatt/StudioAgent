AutoFlow v2.1 (Repo-aligned + Contract-complete)
Date: 2026-01-31

This is an updated v2 plan that **keeps all repo-aligned implementation steps** from v2, while **re-introducing the missing “contracts” and semantics** that v1 required (ChangeSet lifecycle + risk/applyPolicy, late-answer semantics, richer node run logs, QuestionSet UX constitution, debug affordances, “finish without polish”, and audit staleness).

──────────────────────────────────────────────────────────────────────────────
0) Non-Negotiable Product/Runtime Contract (must be true in v2.1)

0.1 Two engines, always decoupled

* Flow Engine: runs gates to completion **without waiting** for user input.
* Clarification Engine: continuously asks small QuestionSets in chat, collects answers, improves future outputs — **never blocks flow**.

0.2 Gate snapshot contract (determinism + debuggability)
When a gate starts, it snapshots:

* artifactRevisionInId = the latest applied artifact revision
* answerVersionUsed = the current answerVersion at gate start
* answerState snapshot at answerVersionUsed
  Rule:
* Inputs do not change mid-run.
* **Late answers DO NOT affect that gate run.**

0.3 Late answer policy (default)

* Do NOT auto-rerun completed gates.
* Late answers influence:

  * future gates (gates that start after the answers exist)
  * the optional final Audit/Polish step
    Optional (later, not required for v2.1 MVP):
* “Selective rerun”: mark some nodes stale and rerun if flow still running.

0.4 Gate output contract
Each gate produces:

* assumptions[] (explicitly listed, if missing data)
* confidence (or confidenceNotes)
* a ChangeSet (+ metadata) describing the proposed edits
* applyPolicy:

  * regular gates: auto
  * audit/polish: manual
* status transitions are tracked (see ChangeSet contract)

0.5 ChangeSet contract (first-class lifecycle)
Every ChangeSet has:

* ops[]: create | patch | archive | link (etc.)
* summary
* riskLevel
* applyPolicy: auto | manual
* status: proposed | applied | rejected | stale
  And every apply attempt is recorded:
* ChangeSetApplyLog: appliedBy, appliedAt, result success|failure, error, artifactRevisionOutId

0.6 QuestionSet UX constitution (chat stays clean)

* QuestionSets are event-triggered (no spam):

  * after gate completion/apply
  * after answer submission (debounced)
  * optional periodic tick ONLY if flow running and no recent questions
* A QuestionSet is small (3–7) and ordered by impact.
* Questions map to canonical fieldKeys so answers are machine-usable.
* Each question includes: questionId, fieldKey, prompt, choices?, priority, whyAsked
* User can ignore indefinitely.
* Answer submission updates answerState immediately.
* The flow does not pause and does not ask for “permission”.

0.7 Debug visibility is rich but never blocking
Debug shows per node:

* status timeline (queued → running → done/failed/stale)
* attempt #
* answerVersionUsed
* artifactRevisionInId → artifactRevisionOutId
* inputsHash (idempotency key)
* assumptions + confidence
* ChangeSet summary + riskLevel + applyPolicy + status
* apply result (success/failure + error)
* logsRef (prompt/trace/token usage/errors)
  Also:
* Provide “download / copy ChangeSet” for troubleshooting.
* Never show blocking modals.

0.8 Audit/Polish contract

* Only appears after flow completes.
* UI shows TWO buttons:

  * “Run Audit & Repair” (recommended)
  * “Finish without polish”
* Audit produces a manual ChangeSet (applyPolicy=manual).
* If answers/artifacts changed since audit started → mark audit stale and recommend rerun.

──────────────────────────────────────────────────────────────────────────────
Validation Summary (from current code)

* Flow Runner is sequential + blocking in `convex/flow/flowRunner.ts`, driven by `flowRuns`/`flowSteps` and validation gates. v2.1 adds a v2 orchestrator path behind a flag.
* Clarification questions are produced by `buildQuestionsBlock` and rendered as `QuestionsBlock` in Flow chat. v2.1 reuses `QuestionsBlock` for non-blocking QuestionSets (no new UI type required).
* Skills runner builds context from live DB (`convex/skills/runner.ts`). v2.1 adds explicit snapshot inputs (artifactRevisionId + answerState snapshot) for determinism.
* ChangeSets already support base snapshots + apply logic. v2.1 adds lifecycle status + apply logs + revision outputs without breaking existing flows.

Phase 2 — Artifact Revisions + Apply Pipeline (with ChangeSet lifecycle)
Tasks

* Create `convex/flow/artifactRevisions.ts`:

  * `createRevisionFromLive(projectId, source)` uses `buildProjectSnapshot`.
  * `createRevisionFromSnapshot(snapshot, meta)` stores snapshot + hash.
  * `applyChangeSetAndCreateRevision(changeSetId, baseRevisionId, appliedBy)`:

    * validates base revision matches changeSet.artifactRevisionInId
    * applies
    * writes ChangeSetApplyLog
    * creates artifactRevisionOutId
    * updates ChangeSet.status -> applied on success; failure logged

* Update `flowRuns.start` (`convex/flowRuns.ts`):

  * create initial artifact revision
  * set `currentArtifactRevisionId`, `answerVersionAtStart`, `latestAnswerVersion`

* Ensure manual apply (existing ChangeSet UI) also writes:

  * apply logs
  * artifact revisions
  * ChangeSet.status transitions (applied/rejected)

Acceptance

* Run start creates revision.
* Auto-apply creates apply logs + advances `currentArtifactRevisionId`.
* Manual apply path also produces logs + revision.

Phase 3 — Non-blocking Orchestrator (DAG) with snapshot semantics
Tasks

* Add DAG config in `convex/flow/graph.ts`:

  * nodes, edges, concurrency limit (start 2–4)
  * label nodes as spine vs safe-branches (examples below)

* Create orchestrator action (e.g., `convex/flow/orchestrator.ts`) that:

  * loads run + `currentArtifactRevisionId` + `latestAnswerVersion`
  * selects ready nodes (deps satisfied) up to concurrency limit
  * for each node start:

    * compute `answerVersionUsed = latestAnswerVersion`
    * write `flowNodeRuns` status=running with `inputsHash`
    * build snapshot-aware context (artifactRevisionId + answerState at answerVersionUsed)
    * run gate skill/validator
    * produce ChangeSet + assumptions + confidence + logsRef
    * set ChangeSet.applyPolicy:

      * regular nodes: auto
      * audit: manual (not part of this phase)
    * auto-apply ChangeSet (regular nodes) via Phase 2 wrapper
    * write node run artifactRevisionOutId + mark done
  * crucial rules:

    * never block for missing info → record assumptions instead
    * inputs are stable per node run (no mid-run changes)

* Route `flowRunner.tick` to v2 orchestrator when `ff_flow_runner_v2` enabled; keep v1 fallback.

Safe branch guidance (keep it sane)

* Sequential spine (typical): Normalize Brief → Ideation → Plan → Tasks → Accounting → Quote → Consolidate
* Safe parallel branches (examples): Risk analysis, Vendor/lead-time research, Print feasibility checklist
* Branches feed into Consolidate (single merge point)

Acceptance

* Flow completes without user answers.
* Node runs have answerVersionUsed + revision ids + assumptions.
* Late answers do not retroactively change completed nodes.

──────────────────────────────────────────────────────────────────────────────
Phase 8 — Hardening + Rollout (idempotency, staleness, replay, parallel safety)
Tasks
Idempotency & locks

* Enforce single apply per (runId, nodeId, inputsHash).
* Use lease/lock for queued→running.
* Retries increment attempt but only apply if still current.

Staleness detection

* If `currentArtifactRevisionId` advances after node start:

  * mark the node run stale
  * skip apply (or record “discarded” outcome)

Parallelism safety

* Start with limited concurrency (2–4) and serialize applies if needed.
* Restrict safe branches to:

  * read-only analyses, or
  * outputs that merge only at Consolidate,
    until a merge strategy is formalized.

Replay tooling

* Rebuild final state from:

  * flowNodeRuns
  * artifact revisions
  * apply logs
* Helpful for debugging and regression tests.

Acceptance

* No duplicate applies.
* Stale runs are detected.
* Replay reproduces end state deterministically.

──────────────────────────────────────────────────────────────────────────────
End State (what “done” means)

* Starting a flow completes without the user answering anything.
* Main chat shows small, event-triggered QuestionSets; user can ignore indefinitely.
* Each gate logs answerVersionUsed and revision in/out, records assumptions/confidence, and auto-applies its ChangeSet.
* Late answers don’t affect already-finished gates (no surprise reruns).
* Debug panel shows full provenance + lets you copy/download ChangeSets.
* After completion, the user can either:

  * Run Audit & Repair (manual ChangeSet + verification), or
  * Finish without polish.
* Audit becomes stale if underlying answers/artifacts change mid-audit.
