# 2) New tables (full schemas)

Below are **complete** Convex table schemas for the new stuff.

## 2.1 `changeSets` (A: ops array in one doc)

**Core idea:** store a stable envelope + `ops[]` where each op is `{ kind, payload }`.
This avoids schema migrations when you add new op types later.

```ts
changeSets: defineTable({
  projectId: v.id("projects"),
  stage: v.union(v.literal("IDEATION"), v.literal("QUOTE"), v.literal("BREAKDOWN")),

  status: v.union(v.literal("PROPOSED"), v.literal("APPLIED"), v.literal("DISCARDED")),

  reason_he: v.string(),

  // Conflict control: list of entities this changeSet expects to be unchanged.
  base: v.optional(v.object({
    elements: v.optional(v.array(v.object({
      elementId: v.id("elements"),
      rev: v.number(),
    }))),
  })),

  // The ops list (A): stable structure
  ops: v.array(v.object({
    kind: v.string(),   // e.g. "element.create", "task.create"
    payload: v.any(),   // validated at runtime in applyChangeSet()
  })),

  // UI preview strings (so you don’t need to compute preview on every render)
  preview_he: v.optional(v.object({
    elements: v.optional(v.array(v.string())),
    tasks: v.optional(v.array(v.string())),
    accounting: v.optional(v.array(v.string())),
    printing: v.optional(v.array(v.string())),
    purchases: v.optional(v.array(v.string())),
  })),

  schemaVersion: v.optional(v.number()), // start with 1

  createdAt: v.number(),
  createdBy_he: v.optional(v.string()),

  appliedAt: v.optional(v.number()),
  appliedBy_he: v.optional(v.string()),

  discardedAt: v.optional(v.number()),
  discardedBy_he: v.optional(v.string()),
})
.index("by_project", ["projectId"])
.index("by_project_status", ["projectId", "status"])
.index("by_project_stage", ["projectId", "stage"]);
```

### The allowed `kind` values (v1)

Keep it small:

* `element.create`
* `element.update`
* `task.create`
* `accountingLine.create`
* `printPart.create`
* `purchase.create` (with allocations + receipt links in payload)

You can add more kinds later without migrations.

# 3) Memory system (your 3 requested memory types)

We’ll implement it as:

1. `memoryDocs` (source docs + their AI summaries)
2. `runningMemory` stored as a `memoryDoc` kind = `RUNNING_MEMORY`
3. `qaPairs` structured table + a digest `memoryDoc` kind = `QA_DIGEST`

## 3.1 `memoryDocs` (documents + AI ingested summary + the “living docs”)

```ts
memoryDocs: defineTable({
  projectId: v.id("projects"),
  elementId: v.optional(v.id("elements")),

  // SOURCE_DOC: vendor quote, brief, PDF, image notes, etc.
  // RUNNING_MEMORY: always-updating user-only summary
  // QA_DIGEST: always-updating digest of Q&A
  kind: v.union(
    v.literal("SOURCE_DOC"),
    v.literal("RUNNING_MEMORY"),
    v.literal("QA_DIGEST")
  ),

  title_he: v.optional(v.string()),

  // Where the doc comes from
  source: v.optional(v.object({
    sourceType: v.union(
      v.literal("FILE"),
      v.literal("TEXT"),
      v.literal("URL"),
      v.literal("CHAT_EXPORT"),
      v.literal("OTHER")
    ),
    fileId: v.optional(v.id("files")), // if FILE
    url: v.optional(v.string()),       // if URL
  })),

  // Optional raw text for small docs (avoid huge blobs; store big stuff in files)
  rawText_he: v.optional(v.string()),

  // AI ingested summary (for SOURCE_DOC)
  aiSummary: v.optional(v.object({
    model: v.string(),         // e.g. "gpt-5-nano"
    summaryMd_he: v.string(),  // short, structured
    facts_he: v.optional(v.array(v.string())),
    updatedAt: v.number(),
  })),

  // For RUNNING_MEMORY / QA_DIGEST: the living markdown document
  contentMd_he: v.optional(v.string()),

  schemaVersion: v.optional(v.number()),

  createdAt: v.number(),
  updatedAt: v.number(),
})
.index("by_project", ["projectId"])
.index("by_project_kind", ["projectId", "kind"])
.index("by_project_element_kind", ["projectId", "elementId", "kind"]);
```

### How you’ll use it

* **Source docs**: upload → create `memoryDocs(kind=SOURCE_DOC, source.fileId=...)` → run ingestion action → store `aiSummary`.
* **Running memory**: exactly one doc per project (and optionally per element if you want later) with `kind=RUNNING_MEMORY`.
* **Q&A digest**: exactly one doc per project with `kind=QA_DIGEST`.

No backfills needed: if a project doesn’t have a RUNNING_MEMORY doc yet, you create it lazily.

## 3.2 `qaPairs` (structured questions & answers)

This is the “don’t ask again” engine.

```ts
qaPairs: defineTable({
  projectId: v.id("projects"),
  elementId: v.optional(v.id("elements")),

  // The actual question that was asked (not invented later)
  question_he: v.string(),

  // Optional stable key to detect repeats (computed server-side)
  questionKey: v.optional(v.string()),

  // The user's answer (from structured UI or parsed)
  answer_he: v.string(),

  // Where it came from
  source: v.object({
    sourceType: v.union(
      v.literal("CLARIFICATION_BLOCK"),
      v.literal("CHAT_PARSE")
    ),
    conversationId: v.optional(v.id("conversations")),
    messageId: v.optional(v.id("conversationMessages")),
  }),

  createdAt: v.number(),
})
.index("by_project", ["projectId"])
.index("by_project_element", ["projectId", "elementId"])
.index("by_project_questionKey", ["projectId", "questionKey"]);
```

### Why both `qaPairs` and `QA_DIGEST` doc?

* `qaPairs` is structured and queryable (avoid repeats).
* `QA_DIGEST` is a single markdown chunk the agent can read fast (context window friendly).

# 4) How tables interact (the full flow)

## 4.1 One chat flow with interactive blocks

1. User message → saved in `conversationMessages(role=user)`
2. Agent replies:

   * plain text OR clarification block OR suggestion block OR changeSet block
3. If agent proposes changes:

   * server creates `changeSets(PROPOSED)`
   * assistant message includes `changeSetId`
4. User clicks Apply:

   * UI calls `applyChangeSet(changeSetId)` (single atomic mutation)
   * server writes an `event` message `changeset_applied` + updates changeSet status

## 4.2 ChangeSet apply (atomic multi-table update)

`applyChangeSet()`:

* checks conflicts (`elements.rev`)
* validates ops
* creates records in correct order (temp mapping)
* updates element revs
* marks changeset APPLIED

If anything fails → nothing is written (atomic).

# 6) The key mutation: `applyChangeSet()` (process plan)

### Steps (exact)

1. Load changeSet, verify `status=PROPOSED`
2. Conflict check:

   * For each `element.update`, load element and compare:

     * `element.rev === payload.baseRev`
   * If mismatch → throw `CONFLICT` with details
3. Validate all ops (hard checks)
4. Execute ops in safe order with temp mapping:

   * A) Create Elements (build `tempElementId → realId`)
   * B) Create PrintParts (resolve element ref)
   * C) Create Tasks (resolve element ref + task dependencies)
   * D) Create Accounting lines
   * E) Create Purchases + allocations + receipt links
   * F) Apply Element updates (and increment rev)
5. Patch changeSet:

   * `status=APPLIED`, `appliedAt=now`

### Safety rules inside apply

* If printing exists but no QA task exists → either:

  * fail with error (strict mode), or
  * auto-create a QA task (recommended)
* If `safetyCritical=true` → auto-create “בדיקת בטיחות/אישור” task

# 7) Memory processes (how the 3 memory types are updated)

## 7.1 Source docs ingestion

When user uploads a document:

1. store file in `files`
2. create `memoryDocs(kind=SOURCE_DOC, source.fileId=...)`
3. run ingestion action:

   * extract text (if needed)
   * summarize with GPT-5-nano (or your preferred model)
4. update `memoryDocs.aiSummary`

No backfill: docs without aiSummary just show “not processed yet”.

---

## 7.2 Running memory (user-only, delta-only)

**Goal:** one always-updating markdown doc with only user inputs summarized.

Process after every user message:

1. call `appendRunningMemory(projectId, elementId?, userText)`
2. it uses GPT-5-nano to create a **delta bullet list** (no dedup)
3. append under headings inside `contentMd_he`

Storage:

* `memoryDocs(kind=RUNNING_MEMORY).contentMd_he`

---

## 7.3 Q&A log (structured + digest)

### Source of truth = `qaPairs`

Two ways to populate:

**A) From ClarificationBlock submissions (best v1)**

* When user submits answers:

  * create `qaPairs` rows for each question+answer
  * update `QA_DIGEST` markdown

**B) From free chat parse (optional v1.5)**

* After user message, nano model detects if it answers a known open question and emits pairs.
* save pairs and update digest.

Digest update:

* `memoryDocs(kind=QA_DIGEST).contentMd_he` is regenerated or appended.

**Why this avoids repeating questions**
Before the agent asks a question, it searches:

* `qaPairs.by_project_questionKey` or scans latest Q&A
  If answered → it shouldn’t ask again, unless user indicates change.
