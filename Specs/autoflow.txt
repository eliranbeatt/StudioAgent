GPT plan:

Below is a full end-to-end plan to implement your new non-blocking Flow Agent:

No blocks / no pauses / no “await user input.”

Gates run automatically (sequential spine + optional parallel branches).

Main chat continuously shows question sets (detached from the flow).

Each gate uses whatever answers exist at gate start (snapshot).

Intermediate ChangeSets are auto-approved/applied (but fully visible in Debug mode).

Final “Polish / Audit & Repair” step is optional and only runs when the user clicks, producing a ChangeSet that requires explicit approval.

0) Target behavior in one sentence

Two independent engines run side-by-side:

Flow Engine runs gates to completion without waiting.

Clarification Engine continuously asks questions, collects answers, and improves future outputs—but never blocks the Flow.

1) Core architecture changes
1.1 Kill “blocks” and replace with runs + snapshots

Before: Gate execution is coupled to UI blocks and can pause on missing info.
After: Gate execution is driven by a backend orchestrator and always proceeds using a snapshot of known answers + artifacts at gate start.

1.2 Introduce three “durable logs”

You’ll stop thinking in terms of “UI state” and instead in terms of append-only logs:

Answer Log

User answers arrive at any time.

You maintain a merged answerState + answerVersion.

Artifact Revisions

Every gate produces a ChangeSet and a resulting artifact revision (applied automatically for regular gates).

Gate Run Log

Every gate run stores inputs hash, snapshots used, output summary, assumptions, and any ChangeSets created/applied.

This is what makes the system deterministic, debuggable, and parallelizable.

2.1 Flow execution

3) Gate execution semantics (the new contract)

Each gate must follow the same lifecycle:

3.1 Gate input = stable snapshot

When a gate starts, it reads:

artifactRevisionInId (latest applied revision)

answerState snapshot at answerVersionUsed

(optional) questionHistory to avoid asking the same thing repeatedly

Rule: once started, it does not change inputs mid-run.

3.2 Gate output = ChangeSet + metadata

A gate produces:

assumptions[] if data was missing

confidence

changeset to update artifacts (elements/tasks/accounting/etc.)

3.3 Auto-approval policy (your requirement)

For all regular gates:

applyPolicy = auto

the system automatically applies the ChangeSet immediately (server-side)

the gate completes and unblocks dependent gates

For the final polish gate:

applyPolicy = manual

nothing is applied until the user clicks “Approve”

4) Flow Orchestrator (how gates run with no pauses)
4.1 Replace “block UI” with a DAG scheduler

Model gates as a DAG:

Nodes = gates

Edges = dependencies (what must exist before another can run)

Then implement a scheduler loop:

Find all nodes with status=queued and whose dependencies are done

Start up to concurrencyLimit nodes

Each node runs independently and writes results

On completion, mark node done, update currentArtifactRevisionId, and schedule the next tick

Continue until all nodes are done

4.2 Sequential spine + safe parallel branches

Don’t parallelize everything. Do this:

Sequential spine (typical):

Normalize Brief → Ideation → Plan → Tasks → Accounting → Quote → Consolidate

Parallel branches (examples):

Risk analysis

Vendor/lead-time research

Print feasibility checklist
These branches feed into Consolidate.

4.3 Idempotency & locking (so “true parallel” is safe)

Every node run uses:

inputsHash = hash(artifactRevisionInId + answerVersionUsed + nodeId + graphVersion)

Only one run per (runId, nodeId, inputsHash) may apply

Use a lease/lock when transitioning queued→running

Retries create attempt+1 but only apply if still current

5) Clarification Engine (always-on questions in the main chat)
5.1 Detached, event-driven question generation (not “continuous spam”)

Generate a new QuestionSet only on triggers:

After gate completion (new artifacts → new unknowns)

After user answers (debounced)

Optional: periodic tick (only if flow still running and no recent questions)

5.2 QuestionSet rules (so it stays clean)

Always derived from:

current artifactRevision

current answerState

previous questions asked + already answered fields

Questions map to canonical fieldKeys so answers are machine-usable.

A QuestionSet should be small (e.g., 3–7 questions) and ordered by “impact.”

5.3 Main chat UX

The main chat shows:

QuestionSet #1 → user answers → QuestionSet #2 → etc.

User can ignore indefinitely.

Answers update answerState immediately.

Importantly: the flow doesn’t pause, and doesn’t “ask for permission.”

6) How gates consume answers without blocking
6.1 Snapshot timing

When gate starts:

it reads answerVersionUsed = currentAnswerVersion

Late answers do not affect that gate run.

6.2 Late answer policy (recommended default)

To keep behavior predictable:

Do not automatically rerun completed gates.

Late answers influence future gates and the optional polish step.

Optionally (later), you can add:

“Mark stale + selective rerun” for specific gates while flow is still running.

7) Debug mode (show everything, but don’t interrupt)

You want auto-approval + full visibility.

7.1 What debug mode shows (per gate)

For each gate node, show:

Status timeline: queued → running → done

answerVersionUsed

artifactRevisionInId → artifactRevisionOutId

Assumptions + confidence

InputsHash (idempotency)

Logs/trace (prompt tokens, errors)

7.2 Where to display it

A Debug panel/side drawer or a “Debug” tab.

Never as blocking modals.

Allow “download / copy ChangeSet” for troubleshooting.

8) Final optional “Polish / Audit & Repair” step (manual trigger)
8.1 When it appears

Only when FlowRun reaches completed:

UI shows:

✅ Flow completed

Button: Run Audit & Repair (recommended)

Button: Finish without polish

8.2 What it does (pipeline)

When clicked, it runs:

Stage A — Deterministic validators

duplicates

etc.

Stage B — GPT-5.2 medium reasoning “deep audit”
Input:

latest answerState

Output:

audit report

a ChangeSet bundle (create/patch/archive/link)

expected improvements

Stage C — Verify

simulate apply

rerun validators

produce before/after metrics

8.3 Approval rules

The polish gate produces a ChangeSet with applyPolicy=manual.

User sees grouped changes:

Link repairs

Dedup merges

Missing fields

Accounting/quote sync

Risky changes (unchecked by default)

User clicks Approve to apply.

If answers/artifacts changed since the audit started, mark it stale and recommend re-run.

Phase 1 — Foundations

10) Acceptance criteria (so you know it’s done)

Starting a flow completes without the user answering anything.

Main chat continuously shows question sets; answering never pauses flow.

Each gate logs answerVersionUsed and applies its ChangeSet automatically.

Debug mode shows every gate, its ChangeSet, and applied state.

After completion, polish is offered and only runs on click.

Polish produces a manual ChangeSet; nothing changes until approval.

After applying polish, validators show improved metrics (fewer duplicates/orphans/mismatches).


code based plan:
Below is a repo-aligned implementation plan that maps your non‑blocking Flow Agent requirements onto the existing Flow Agent backend/frontend structure. I’m grounding the plan in what’s currently implemented (flow runs/steps, validation gates, chat blocks, and change sets) and then outlining the precise deltas needed to introduce durable logs, snapshots, non‑blocking gate execution, and the optional audit step. Citations reference the current code and schema so you can trace each recommendation to its starting point.

Current state (from the codebase)
Flow orchestration + gating (today)
The flow runner is a single sequential “tick” loop that advances through G0 → G10, runs validation, and blocks when a gate fails validation. It emits FlowGateBlock and FlowBrainDumpBlock messages and, if autoApprove is on, it auto‑applies ChangeSets. This is all in convex/flow/flowRunner.ts.

The runner depends on the flowRuns and flowSteps tables to track the current gate, statuses, and draft ChangeSet IDs.

Flow is tied to chat messages via the flow.chat.* API, which stores agentMessages in agentConversations and triggers the runner when new user messages arrive.

Clarifications (today)
Clarifications are built from validation blocking issues into a QuestionsBlock via buildQuestionsBlock, which uses QA pairs, unknown‑accepted keys, and dismissed opportunities to filter questions.

Answers are currently stored as QA pairs (qaPairs table) via flowAnswers.submitAnswers, and some “accept unknown / dismiss” actions patch projects state directly.

FlowGateBlock handles submission (ask more / advance / skip) and then triggers flowRunner.tick, which is another blocking linkage between the UI and gate execution.

ChangeSet application (today)
The flow runner auto‑applies ChangeSets by calling changeSets.applyChangeSetOps, then emits FlowChangeSetSummaryBlock to the chat when auto‑approve is enabled.

The Flow Agent page shows a chat‑first layout with debug/timeline panels and run toggles, but these are still tied to the blocking run model and gate-based flow steps.

Snapshots (today)
There is already a snapshot builder (buildProjectSnapshot) that creates a full project snapshot (project, elements, tasks, lines, etc.). This can be reused as the basis for artifact revisions.

Implementation plan (repo‑aligned)
1) Add durable logs + snapshot-aware data model
Goal: create the three durable logs + audit constructs described in your plan, without breaking existing flowRuns/flowSteps.

Schema updates (new tables + new fields)

Extend flowRuns with:

graphVersion

currentArtifactRevisionId

answerVersionAtStart

debugModeEnabled

(Optional) latestAnswerVersion for quick access
_Existing flowRuns already stores currentGateId, status, and toggles; we’ll add these alongside the current fields._

Introduce new tables (in convex/schema.ts):

flowNodeRuns (gate run log: inputs hash, snapshots, assumptions, changeSet refs)

flowAnswerEvents (append‑only answer log with answerVersion)

flowQuestionSets (question set log + metadata)

flowChangeSetApplyLogs (applied changeSets + artifact revision outputs)

flowAuditRuns (polish/audit logs + findings + changeSet id)

Preserve existing flowSteps for backwards compatibility; use them as “legacy” gate runs until the new logs take over.

Why this aligns with code:
The flow runner and UI already expect flowRuns and flowSteps records. Adding new tables lets us introduce the log‑based model without breaking existing runtime assumptions.

2) Artifact revisions + ChangeSet apply pipeline
Goal: ensure every gate reads a stable snapshot and produces a ChangeSet that results in a new artifact revision.

Backend changes

Create convex/flow/artifactRevisions.ts:

createRevisionFromLive(projectId, source) → uses buildProjectSnapshot and saves to flowArtifactRevisions.

applyChangeSetAndRevision(changeSetId, baseRevisionId) → apply ops and generate new revision.

Hook into changeSets.applyChangeSetOps or add a new wrapper so that any auto‑applied ChangeSet (or manual approval) produces a flowChangeSetApplyLog entry + updated artifact revision pointer.

Update flowRuns.start to generate the first flowArtifactRevision and store it in flowRuns.currentArtifactRevisionId. Currently flowRuns.start just creates a run and enqueues the runner; this is where the initial snapshot should be inserted.

3) Replace the blocking runner with a DAG orchestrator
Goal: eliminate blocking and run gates with snapshots + answer version.

Implementation steps

Create a new orchestrator action (e.g., convex/flow/orchestrator.ts) that replaces the blocking logic in flowRunner.tick. It should:

Load flowRuns.currentArtifactRevisionId and the latest answerVersion.

Find ready nodes from a DAG definition (new file convex/flow/graph.ts).

Start FlowNodeRun entries for each ready node (respect concurrency limits).

Run gate logic (validators, skills, changeSet creation).

Auto‑apply ChangeSets for regular gates, update currentArtifactRevisionId, and log outcomes.

Move gate order from flowRunner.tick into DAG config. Today the order is hard‑coded (G0‑G10) and the runner blocks on validation issues.

Change blocking semantics: instead of returning on failed validation, gather assumptions + confidence and proceed. The gate’s FlowNodeRun should record:

assumptions[]

confidence

answerVersionUsed

inputsHash

Idempotency + locking: use inputsHash (same hashing approach as today’s gate dedupe hash) to guarantee only one apply per (runId, nodeId, inputsHash) and mark “stale” runs if out of date.

Why this aligns with code:
The existing flowRunner.tick is a sequential, blocking loop that emits gate blocks and returns when a gate is blocked. We’ll replace that with a scheduler that never blocks, but we can reuse runSkillForGate patterns and ChangeSet application logic from the existing runner.

4) Clarification engine (detached from flow)
Goal: always‑on questions in chat, but never block the flow.

Backend changes

Add flowQuestionSets + flowAnswerEvents tables.

Build a new “QuestionSet generator” that uses:

flowArtifactRevision (current snapshot)

answerState (derived from flowAnswerEvents)

last question sets (to avoid duplicates)

Trigger question set generation:

After each gate completes (or after ChangeSet apply)

After flowAnswerEvents write (debounced)

Keep using buildQuestionsBlock as a scoring/priority helper but remove the dependency on “blocking issues” to gate flow execution.

Frontend changes

Add a new block component (e.g., FlowQuestionSetBlock) for chat rendering alongside existing block types in FlowChat’s renderer. Right now FlowChat is set up to render QuestionsBlock and FlowGateBlock from messages; you’ll add a new block type for non‑blocking question sets and route answer submissions to the new answer log endpoint.

5) Gate execution contract (snapshot + ChangeSet)
Goal: every gate reads a stable snapshot and produces a ChangeSet, never blocking.

Implementation detail

Store artifactRevisionInId

Store answerVersionUsed

Read answerState as of that version

auto‑apply for non‑polish gates

Update runSkillForGate to accept artifactRevisionInId and answerSnapshot (or at minimum, include revision id in skill params for traceability).

Why this aligns with code:
The current flow runner uses buildProjectSnapshot for validation reports and then runs skills to produce ChangeSets. This can be reused but gated by a new snapshot‑first contract rather than live state plus blocking validation checks.

6) Debug mode + logs surfaced in UI
Goal: show full provenance without blocking the flow.

Frontend changes

Update FlowDebugPanel and FlowTimeline to read from flowNodeRuns and flowChangeSetApplyLogs rather than legacy flowSteps.

Add UI fields for answerVersionUsed, artifactRevisionIn/Out, inputsHash, assumptions/confidence.

Keep the existing debug toggle in FlowAgentPage, just wire it to the new log sources.

7) Optional Audit & Repair step (manual approval)
Goal: manual “Polish/Audit & Repair” after flow completion.

Backend

Add flowAuditRuns table and an audit.run action:

Stage A: deterministic validators (can reuse validation functions already imported in flowRuns.ts).

Stage B: LLM audit → ChangeSet proposal (manual apply).

Stage C: verify metrics before/after.

Store artifactRevisionUsed + answerVersionUsed to detect staleness.

Frontend

When FlowRun.status === completed, show:

Button: “Run Audit & Repair”

Button: “Finish without polish”

Render the resulting audit ChangeSet in the chat (manual approval in ChangeSetReviewDrawer already exists).

8) Migration + rollout
Goal: transition safely without breaking current runs.

Steps

Phase 1: Add new tables + write paths (logs, revisions) without turning off old flowSteps. Keep flowRunner.tick but begin storing flowNodeRuns + flowArtifactRevisions in parallel.

Phase 2: Introduce orchestrator with a feature flag (e.g., ff_flow_runner_v2) and route flowRuns.runNext to it when enabled.

Phase 3: Replace FlowGateBlock blocking semantics with non‑blocking question sets and retire forceQuestionGateId in flowRuns.
(You can keep the component but use it only for debugging or admin override if needed.)

Phase 4: Add audit pipeline + manual approval.
