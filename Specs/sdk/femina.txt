Below is the **full dev plan** (English), implementing **everything you asked for** across domains, prompts, runtime flow, schemas, and UI—based on your prompt file + your answers:

* **No “always ask questions”** rule.
* **Only Clarification Agent asks questions (4–8)** when needed.
* **Suggestions every turn (1–3)**, *not restricted to predefined skills*—any next action, route, prompt, or workflow.
* **Assignments are name-only** (no employee IDs stored in tasks/lines).
* **Migrate labor costing to days** (10 hours per day).
* **Free chat is truly free**: short replies or deep research outputs, not restricted to short templates.
* Add a **Deep Thinking / Research Agent skill** (GPT-5.2 medium + web search) that the chat (GPT-5-mini minimal) can invoke only when needed.
* **External contractors are material lines** (service purchases), priced by Pricing Agent.
* Add an **Audit+Fix Agent** that auto-fixes by calling other tools and compiles a ChangeSet proposal.

# 3) Updated UX contract (what each turn returns)

## Chat turns (Orchestrator / Free Chat)

* **No mandatory questions.**
* Always include:

  * `ChatBlock` (can be short OR long, multi-paragraph, research-level)
  * `SuggestionsBlock` (1–3 suggestions)
* `QuestionsBlock` appears only if:

  * user invoked Clarify agent or Preview+Questions output is being shown.

## Suggestions are NOT limited to predefined skills

Suggestions can be any “next action”, e.g.:

* “Run Clarification set (4–8 questions)”
* “Generate Preview Plan + full open questions list”
* “Compile ChangeSet from latest intents”
* “Open /management/employees”
* “Run Deep Thinking research on X”
* “Create task batch for element Y”
* “Patch labor days for tasks in element Z”

**Implementation detail:** suggestions should be typed actions in the UI (see §8).

# 4) Prompt changes (exactly what to implement in `convex/sdk/prompts.ts`)

## 4.1 ORCHESTRATOR_SYSTEM — remove forced questions, free-form suggestions, deep-thinking wiring

### Changes to make

1. **Remove**: “Every chat turn must return exactly 1 QuestionsBlock with one question.”
2. **Replace with**:

   * Orchestrator **does not ask questions directly**.
   * If blocked → call `clarify.next_questions`.
   * If user wants big-picture gaps → suggest `draft.plan_and_questions`.
3. Suggestions:

   * Always output `SuggestionsBlock` with **1–3** suggestions.
   * Suggestions can be any next step (not only tool calls).
4. Deep Thinking wiring:

   * Add a rule: if the user asks for deep research / strategy / analysis, call `think.deep`.
   * Orchestrator stays fast; it delegates slow thinking.

**Result:** Chat becomes natural and flexible, but still action-driven.

---

## 4.2 FREE_CHAT_SYSTEM — “free means free” + can trigger deep research

### Changes to make

* Remove “restricted short format” mindset.
* Allow:

  * short answers
  * long answers
  * deep research answers (by delegating to `think.deep`)
* Free chat itself still should not start heavy plan/cost flows unless user asks.

**New rule**

* Free chat may respond fully. If the answer requires deep research, it should:

  * invoke `think.deep`, then present the result in `ChatBlock`.
* It should **not** ask questions directly. If info is needed, it suggests Clarify.

---

## 4.3 CLARIFY_SYSTEM — enforce 4–8 questions, include employee assignment questions

### Changes to make

1. Enforce: **4–8 questions per run** (prefer 4–6).
2. Add assignment questions when labor planning is relevant:

   * “Who will do carpentry tasks?” etc.
   * Options list comes from `context.get employees[]` (names only).
   * Default selected option: “ליאב”.
   * Include “לא יודע כרגע” / “Unknown” option when needed.
3. Output remains JSON-only, includes `blocks` with one QuestionsBlock.

---

## 4.4 PLAN_TASKS_SYSTEM — add assignment (name-only) + detailed tasks + checkpoints

### Changes to schema output

Add fields per task:

* `assigneeNameHe: string | null` (default “ליאב” when reasonable, else null)
* Keep existing `checklist` object array + `checklistHe` fallback (per your request)

Strengthen prompt requirements:

* Each task must include:

  * practical `descriptionHe` (“how we’ll do it”)
  * 3–8 atomic checklist items for execution-heavy tasks
  * meaningful dependencies when real blockers exist

---

## 4.5 COST_BUDGET_SYSTEM — migrate labor from hours → days (10h/day), assign by name

### Required changes

1. Replace `workLines.hours` with:

* `days: number` (allow 0.5 increments)
* `dayHours: 10`
* `assigneeNameHe: string | null`
* `dayRateIls: number | null` (snapshot used for costing; can be updated later)

2. Labor conversion rule (must be in prompt):

* `days = roundToHalf(totalTaskHours / 10)`

3. Default labor cost rule:

* If `assigneeNameHe` is missing:

  * assume “ליאב” unless clearly inappropriate
* If rate missing:

  * assume 1000 ILS/day (low/medium confidence with assumptions)

4. External contractors rule:

* Never create a `workLine` for subcontractors.
* Create a **materialLine** for the service:

  * `sectionKey: "subcontract_services"`
  * `unitHe: "service"` or `"job"`
  * price resolved by pricing agent

---

## 4.6 PRICING_SYSTEM — price materials + services + fill labor day rates

### Changes to implement

1. Expand mission:

* Price material lines, including subcontractor service lines.
* Fill missing studio labor dayRate (and/or compute labor line totals if needed).

2. Labor pricing behavior:

* If a `workLine` has missing `dayRateIls`:

  * match by `assigneeNameHe` in employees list
  * else default 1000/day
* Never leave labor unpriced if it’s studio work.

3. Keep same JSON structure but extend `intent.updates` to support:

* material line updates (unitPrice)
* work line updates (dayRateIls, currency, assumptions, confidence)

## 4.7 AUDIT_SYSTEM → add `AUDIT_FIX_SYSTEM` (auto-fix agent)

### New prompt: `AUDIT_FIX_SYSTEM`

Tools allowed:

* `context.get`
* `plan.tasks`
* `cost.build_budget`
* `pricing.resolve_lines`
* `changeset.compile`
* (optional) `changeset.review`

Behavior:

1. Detect issues (same checks as audit.project).
2. Auto-fix deterministically by calling the appropriate tools:

   * missing tasks structure → re-run `plan.tasks` with current context
   * missing coverage in budget → re-run `cost.build_budget`
   * missing prices → run `pricing.resolve_lines`
3. Compile ChangeSet proposal.
4. Return:

   * summary of fixes
   * compiled ChangeSet proposal (approval gated)
   * remaining risks / assumptions

## 4.8 New Deep Thinking agent: `THINK_DEEP_SYSTEM`

### Purpose

A tool-using agent designed for “slow, high-quality reasoning + web research”.

Tools allowed:

* `web_search` (internet search)
* `context.get` (optional; use if project context needed)
* `knowledge.summarize_or_update` (optional, if you want to store key findings)

Output contract (JSON):

* `answerHe` (or `answer` if you want English output here; but your system is Hebrew-first—choose one consistently)
* `keyFindings[]`
* `sources[]` (URLs or citations if your web tool returns them)
* `recommendedNextActions[]` (used by Orchestrator for suggestions)

**Important:** `think.deep` does **not** mutate DB and does **not** create ChangeSets.
