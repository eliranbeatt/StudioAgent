### Phase 3 — Async rebasing (mini model updates docs)

This is your key optimization and it’s totally sane.

**Mechanics:**

* On every submit, enqueue `plan.update_from_answers`:

  * Inputs: (a) current plan doc, (b) current backlog doc, (c) new answers, (d) any newly ingested files since last update
  * Outputs: updated plan doc + updated backlog doc + “diff summary” (what changed)

**How to implement async robustly:**

* Use OpenAI **background mode** for the update call (or run it via Convex scheduler). Background responses are a first-class pattern for long tasks and can be streamed/resumed. ([OpenAI Platform][1])
* Add **versioning + CAS**:

  * backlog has `version`
  * updater writes only if version matches; otherwise it re-reads and retries once (prevents race conditions)

**Important rule:** updater **never reorders** already-queued QuestionSets that the user hasn’t seen yet unless it’s necessary; it can:

* mark some questions “resolved by answer”
* add new questions at the end (or right after the relevant section)
* raise a blocker to higher priority only if it truly blocks downstream

# 3) Deterministic question serving (code)

## 3.1 Ordering strategy: blockers → element-by-element

Implement `questions.next_set(projectId)` purely in code.

### Bucket order

1. `project blocker`
2. `element blocker`
3. `project helpful`
4. `element helpful`
5. `project optional`
6. `element optional`

### Element order

Use PlanDoc’s element index ordering (`orderIndex`).

### Set size

* default N = 6–8

## 3.2 orderKey format

Make ordering stable across regenerations:

`orderKey = "<bucketCode>/<elementOrderOr000>/<sectionPath>/<createdOrdinal>"`

* `bucketCode`: `PB EB PH EH PO EO`
* `elementOrderOr000`: `000` for project scope
* `sectionPath`: stable grouping
* `createdOrdinal`: monotonic integer per project (assigned in DB on insert)

## 3.3 Cursor design (important)

**Do not** store “next question id”.
Store:

* `lastServedOrderKey` (string) **and** timestamp

When selecting next set:

* find first open question with `orderKey > lastServedOrderKey`
* BUT if new **project blockers** appear, allow jump “back” (because blockers always win)

This is what makes regeneration safe.

# 4) Async rebase + full question regeneration (mini model)

This is the heart of your design.

## 4.1 Trigger

Every time user submits answers:

* persist answers immediately
* enqueue async job `plan.rebase_and_regenerate_questions_async`

## 4.2 Inputs to the updater (minimal but sufficient)

* `projectId`
* `planDoc.current`
* `planDoc.version`
* `elementIndex` (stable keys + order)
* `deltaAnswers`: the newly submitted qapairs (ids + Q + A)
* `qapairsSnapshotSummary`: list of open/answered counts per scopeKey + recent open questions
* new ingested files since last update (optional)

## 4.3 Outputs

Updater returns a **patch**:

1. `planDocPatch` (or full new markdown)
2. `questionsPatch` with operations:

   * `add[]` new questions (with scopeKey, sectionPath, blockingLevel, questionType)
   * `resolve[]` questionIds to mark as answered/dismissed because they’re now redundant
   * `promote[]` questionIds to change blockingLevel (rare)
   * `dedupe[]` mapping from newQ → existingQ

## 4.4 Regeneration rules (to avoid chaos)

Hard rules enforced in code when applying patch:

1. **Never rewrite history**

* existing answered/assumed questions remain
* never delete; only `dismissed`

2. **Never “reopen” answered**

* if new info requires more detail, create **followUp** question(s)
* set `followUp=true` and `triggeredBy=[...]`

3. **Churn limit**

* cap new questions per submit, e.g. `<= 10`
* if more, put overflow into helpful/optional at the end

4. **Blocker discipline**

* only promote to blocker if it truly blocks production/quote correctness

5. **Semantic dedupe**

* if dedupeKey matches, don’t add
* if the model adds something similar, merge into existing open question

## 4.5 Concurrency safety (CAS)

When applying updater output:

* require `planDoc.version` match
* if mismatch:

  * re-read latest and re-run updater once (or drop patch and enqueue again)
