Here’s a **full, detailed implementation plan** to build your **new Agent SDK–based v2 agent system** *in parallel* to the existing (legacy) skills/agents system — with **separate files, separate registries, separate runners**, and a clean cutover path so you can delete the old system later with minimal dead code.

This plan is grounded in your current **Next.js App Router + Convex** console architecture, routes, tables, and existing agents tooling. 
It also follows your studio workflow + language rules and pricing/taskcraft conventions.  

---

## 0) Goals, constraints, and the “no-dead-code” approach

### Goals

1. Build **v2** using the **OpenAI Agents SDK** with your new split:

   * **Option A: Skill Agents** (agentic, looping, branchy)
   * **Option B: Skills as Tools** (one-shot, strict structured output)
2. Keep the **legacy system fully operational** during v2 development.
3. Make v2 **cleanly removable** later:

   * You can delete the legacy code without losing v2.
4. Preserve your “write wall” principle:

   * **Only ChangeSet tools** can cause DB mutations (and apply is approval-gated).

### Key constraints from your system

* Your app already has project-scoped pages (Clarification, Planning, Solutioning, Tasks, Quote, Accounting, etc.), Convex tables, and agent telemetry patterns. 
* Your studio workflow requires consistent mapping: **Projects → Elements → Tasks → Accounting → Quote**, plus procurement, printing QA, execution planning.  
* Language rule: **instructions in English, user-facing Hebrew**, JSON keys in English. 

### The “parallel system” rule

We’ll create a **v2 namespace** across code and optional metadata:

* New folders: `agents_v2/`, `skills_v2/`, `runner_v2/`, `schemas_v2/`
* New registries, prompts, and “SDK runner”
* Feature flag to switch per project/session

You can then delete the legacy folder tree and its wiring when v2 is stable.

## 1) Target architecture (v2)

### 1.1 Components (v2)

**A) Main Orchestrator Agent (v2)**

* Responsible for stage management + delegation.
* Never writes DB directly.
* Always uses:

  * `context.get` (tool)
  * Option A agents (as tools) and Option B skills (as tools)
  * ChangeSet compile/review/apply tool chain

**B) Option A Skill Agents (v2)**
Agentic/iterative tools (sub-agents) you specified:

* procurement.shopping_plan (Agent)

* audit.project (Agent)
* qa.print_files (Agent)
* clarify.next_questions (Agent, with knowledge updates per loop)
* maint.sync_and_repair (Agent, iterative repair sets)

**C) Option B Skills-as-Tools (v2)**
Strict, one-shot, schema-only:

* intake.parse_brief
* plan.elements
* plan.tasks
* plan.execution_phases
* runbook.installation
* ops.daily_plan
* cost.build_budget
* quote.generate
* changeset.compile / review / apply (tools; deterministic/gated)
* admin.set_labor_rates / admin.confirm_measurements

**D) Core tools (v2)**

* `context.get` (non-LLM, deterministic)
* `knowledge.summarize_or_update` (single LLM call tool)
* `changeset.compile` (deterministic transform; minimal creativity)
* `changeset.review` (validator)
* `changeset.apply` (approval-gated)

### 1.2 Where v2 runs (recommended)

Keep v2 “engine” in **Next.js server-side** (Route Handler / Server Action) and talk to Convex via client:

* Pros: easy Node SDK usage, streaming, web tools.
* Keeps Convex actions simpler (data reads/writes).
* Fits your current UI that triggers agents via buttons and displays run telemetry. 

(If you prefer running the SDK inside Convex actions, we can do it too — but separation is cleaner when you want to delete legacy later.)

## 6) Implement the “Write Wall” (ChangeSet chain)

### 6.1 `changeset.compile` (tool, deterministic)

**Input**

* `currentSnapshot` (includes IDs)
* `intents[]` (from Option A/B tools)
* `policy` (allowed operations, deletion rules, etc.)

**Output**

* `ChangeSet` with operations:

  * create/update/delete for tasks, elements, lines, etc.
  * includes safety metadata (risk flags)

**Rules**

* minimal creativity: no new content, only transform intents into exact operations
* strict ID usage: never invent IDs

### 6.2 `changeset.review` (tool)

Validate:

* schema correctness
* referential integrity (task element exists, accounting links valid)
* risky deletes
* duplicate operations
* missing required fields

### 6.3 `changeset.apply` (tool; approval-gated)

* Does the actual Convex mutations, in a transaction-like sequence
* Must support “dryRun” for testing
* Must emit telemetry events so UI can show progress

This matches your existing workflow of human gating before data mutation.

### Phase 4 — Implement Option A Skill Agents (agentic sub-agents)

Build each as a standalone agent with:

* its own system prompt
* its own toolset (limited)
* ability to loop internally and then return final structured output

#### A1) Clarification Agent (highest leverage)

Must:

* loop: ask → update working knowledge doc → decide advance stage
* output next question set + “ready to advance” boolean

**Acceptance criteria**

* After 1–3 loops, it reliably stops asking and advances when sufficient.

#### A2) Pricing Agent

Must:

* catalog lookup → web research → fallback estimate
* normalize units, attach sources, compute confidence
* return “price updates intent” only (no DB writes)

#### A3) Procurement Agent

Must:

* vendor plan, alternates, delivery schedule, risks
* return structured shopping plan intent

#### A4) Audit/Critic Agent

Must:

* run checks (duplicates, missing prices, missing links, quote inconsistencies, risk hotspots)
* propose fix intents
* optionally re-check (or simulate re-check) before returning

#### A5) Receipt Agent

Must:

* parse messy input formats
* propose mappings and uncertainties
* produce a “needs human confirm” list

#### A6) Print QA Agent

Must:

* validate print part requirements against uploaded artifacts and spec (even if metadata-only at first)
* return blockers + fixes
  Printing QA is explicitly recommended by your workflow playbook as a dedicated sub-workstream. 

#### A7) Maintenance Agent

Must:

* iterative fix set A → sanity re-audit → fix set B

**Acceptance criteria (Option A overall)**

* Each agent produces deterministic-ish structured output
* Agents never call changeset.apply
* Agents can be run independently (for debugging)

### Phase 6 — UI integration (minimal + safe)

Add a **single entrypoint UI** for v2 so you don’t rebuild all pages at once:

Option 1 (recommended): a new page/tab:

* `/projects/[id]/agent-v2`
* A single chat-like “guided flow”
* Shows:

  * stage
  * questions
  * suggested actions
  * ChangeSet summary + approve button

Option 2: add a v2 toggle inside existing tabs (Clarification/Planning/etc.)

* Faster, but you’ll touch more UI surfaces.

**Acceptance criteria**

* You can complete a project flow without jumping tabs.

---

### Phase 7 — Evaluation & hardening (so you can delete legacy safely)

Build an eval harness:

* Use 5–10 representative projects
* For each stage:

  * run legacy output
  * run v2 output (dryRun apply)
  * compare:

    * number of elements
    * tasks coverage by stage (buy/build/install/teardown)
    * missing prices rate
    * audit findings count
    * total budget variance
      This is directly aligned with your “pricing from tasks” reality. 

**Acceptance criteria**

* v2 consistently meets or exceeds legacy on:

  * fewer missing lines
  * fewer duplicates
  * more explicit assumptions
  * fewer “surprises” in execution planning

---

### Phase 8 — Cutover & deletion plan (no trash)

Once v2 is stable:

1. Default flag ON for new projects
2. Keep legacy only behind a fallback toggle for 1–2 weeks
3. Remove legacy wiring:

   * delete old runner files and registries
   * remove old UI buttons/handlers
   * remove old prompt store UI if replaced
4. Keep migration notes for old data stored in tables (usually no need to delete tables; only code)
